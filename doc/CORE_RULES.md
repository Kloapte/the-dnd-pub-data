# Core Rules Foundation

The Core Rules Foundation provides canonical identities and interpreted mechanics for actions, rules, skills, conditions, diseases, statuses, senses, and languages. Contracts use JSON Schema Draft 2020-12 and are stored under `src/main/resources/schemas/<model>/schema.json`.

## Canonical entity shape

Each entity has a stable `id` and display `name`. Source attribution is grouped in `sourceMetadata`, which records the exact source code, supplied page, publication flags, citations, and explicit reprint references. A supplied `false` flag remains meaningful. Source-specific interpretations and different editions retain distinct identities; reprints do not imply equivalence or automatic merging.

IDs follow `<type>:<source>:<slug>`, for example `action:phb:attack`. The type is the lowercase canonical model token. Create both the source component and name slug deterministically: apply Unicode NFKD normalization, remove combining marks, lowercase with locale-independent rules, retain ASCII letters and digits, encode remaining non-ASCII letters as `u` followed by their lowercase hexadecimal code point, convert punctuation and whitespace runs to one hyphen, and trim leading and trailing hyphens. If the result is empty, use `u` followed by the lowercase hexadecimal UTF-8 bytes of the original value. Keep the original display name and exact source code unchanged in the entity. Validate uniqueness after normalization; report collisions for explicit adjudication rather than silently renaming or merging entities.

Shared references contain a `targetType` and canonical target `id`. A `relationship` describes the relationship between entities; an `operation` describes a mechanical operation. Neither changes the referenced target type. References are created only from explicit source evidence. Targets in later domains can be referenced by stable identity without embedding their complete models.

Canonical records contain interpreted domain facts and mechanics, not source `entries`, rich-text, font data, or presentation flags such as `hasFluff` and `hasFluffImages`. Do not store review or interpretation status in canonical JSON. Record complete omitted or duplicate source content and its source-object identity in the corresponding model's `omitted.md` or `duplicate.md` register when conversion identifies it. Partial interpretations retain supported mechanics while recording the complete source entry and affected portions in the omission register.

## Domain contracts and use cases

| Model | Contract responsibility | Example use case |
| --- | --- | --- |
| Action | Explicit capabilities, optional typed timing, requirements, typed references, and domain-specific operations for supported attacks, checks, modifiers, state changes, movement, interactions, spell activation, and recovery. A voluntary movement operation can represent dragging or carrying a creature held by Grappled, including its speed cost and size exception. | Represent Mark's opportunity-attack advantage with its actor, target, trigger, duration, usage limit, and reaction behavior; represent Grapple's check, condition application, release, and movement while holding the target. |
| Rule | A Rule identity is valid with source metadata and `ruleType` even when `mechanics` is absent. When mechanics are present, one Rule identity may contain multiple domain-specific components, each with a stable local `componentId`; `kind` identifies its family and `subtype` its procedure. Optional `composition` groups component references with `AND` or `OR`; it does not imply execution order or conditional applicability. Rule mechanics also include bounded D20 procedures, cover degrees, grid-qualified Flanking, skill/ability variation, proficiency, and passive-score construction. | Represent a reference-only Rule by its stable identity without placeholder mechanics. Represent Critical Hit with an attack-roll component and a damage modifier that applies on that component's critical result. Represent standard Cover with source-defined AC/Dexterity-save bonuses or direct-targeting restriction. |
| Skill | Stable skill identity and its explicit ability association. | Associate Acrobatics with Dexterity without copying its descriptive examples. |
| Condition | Ongoing activity restrictions, relational targeting and roll effects, automatic saving-throw failures, condition application/immunity and persistence, movement constraints, critical-hit outcomes, and bounded physical-state consequences, alongside sense and level mechanics. | Resolve Charmed restrictions relative to its charmer, Frightened effects while its fear source is visible, or Incapacitated's edition-specific activity restrictions. Keep each edition's Condition identity and mechanics separate. |
| Disease | Disease-specific applicability, exposure and infection, randomized incubation, symptoms, condition-level restrictions, saving-throw progression branches, and recovery fields where source evidence supports them. Disease-local IDs link temporary symptoms, progression, and DC tracks. | Represent Sewer Plague's incubation, Exhaustion-gated rest effects, daily save outcomes, and zero-level termination. Represent Cackle Fever's stress, temporary laughter, spread, and recovery procedure without flattening them into one linear progression. |
| Status | State thresholds, turn restrictions, maintenance saves, and ending conditions. A source-defined optional save may be marked as DM-required only when the source grants that discretion. | Detect Bloodied at half hit points; evaluate Concentration and Surprised according to their source edition. |
| Sense | Qualitative perception capabilities, restrictions, location precision, illusion interactions, and condition interactions. Numeric ranges belong to the creature that provides the sense. | Apply Darkvision's independent dim-light and darkness transformations, or distinguish Tremorsense pinpointing by edition while using the creature's range separately. |
| Language | Language category, script name, origin, dialect relationships, typed creature-speaker selectors, bounded concealed-message capabilities, and explicit intelligibility relations. | Filter by a resolved creature, supported creature type, or exact source tag; represent source-defined concealed-message recognition and comprehension; distinguish spoken mutual intelligibility from writing systems. |

Action timing is optional. Action, bonus action, reaction, free, and fixed in-game durations use typed timing objects. `alternatives` holds explicit source-supported alternatives; `varied_gametime` preserves open-ended in-game time without a guessed duration or closed option list. Missing timing stays absent. Reaction triggers use typed trigger objects with source-supported kinds, not free-text descriptions.

Action operations use typed event triggers and typed outcomes. Event triggers are distinct from persistent predicates: for example, `GRAPPLER_RELEASES` is an event, while `HAS_CONDITION` and `SPEED_IS_ZERO` describe state. Predicates identify actor and target roles and use a typed Condition reference when one applies. Roll modifiers reuse the shared `D20_ROLL_MODIFIER` value while retaining Action-specific actor, target, applicable roll and ability, conditions, duration, and usage constraints. Condition application and removal are separate operations from Status termination, and identify the recipient creature separately from the referenced Condition or Status. Check and save results are linked to follow-on operations by local `operationId`; a check result is not copied into an outcome string. Grappled-target movement is voluntary drag/carry movement, not forced movement, and retains the source's half-Speed cost and two-size exception.

Action `choiceGroups` define their own cardinality, trigger, and member operation IDs. Each member applies only when its group is selected, after that group’s trigger occurs. The validator checks group and operation identity, membership, cardinality, trigger compatibility, and applicability consistency. This lets a choice represent an exactly-one outcome, as in Shove, without making all Action choices share that cardinality.

Action movement operations distinguish permission to traverse a hostile creature's space (`TRAVERSE_CREATURE_SPACE`), entering and moving with a larger creature (`ENTER_CREATURE_SPACE`), and moving a target laterally into a valid space within reach (`MOVE_TARGET_TO_SPACE_WITHIN_REACH`). These operations link check-gated outcomes to their check IDs; they do not define encounter spatial execution. PHB and XPHB Opportunity Attacks retain separate movement-source rules and immediate-before-departure reaction timing. A movement-increase operation may select a source-defined special Speed for each use where that edition allows it.

Action checks may pair an ability with its Skill in each selectable option. Bounded procedures link attack rolls, checks, modifiers, and outcomes through local operation IDs; finite DC formulas cover a fixed value plus a referenced Spell level and the greater of a minimum and a target ability score. Help choices, Hide, Influence, Spell identification, and skill-task guidance have distinct typed structures. Search and Study task guidance is advisory and does not select or execute a check. `OBJECT_USE` represents an object use that costs an Action; an ordinary object interaction remains separate and can state the PHB one-free-interaction limit and its placement during movement or an Action.

Rule composition references local `componentId` values rather than copying component definitions. A Rule may omit `mechanics` when no mechanics are represented; that does not imply FULL mechanical coverage. Rule references resolve against the pinned Rule source identities and do not require the target to contain mechanics. A nested `AND` means all referenced components participate; `OR` identifies source-supported alternatives. Components carry separate typed `appliesWhen` relationships such as `ON_HIT`, `ON_FAILED_SAVE`, or `ON_CRITICAL_HIT`. Composition does not establish order, trigger, or conditional applicability. For example, Unarmed Strike presents Damage, Grapple, and Shove as alternatives; the Grapple and Shove outcomes share one saving-throw component and apply on its failed result. Unarmed Grapple and Shove options each state their five-foot reach. Difficult Terrain's movement cost is paired with typed qualifying-space predicates, including its source-defined DM-adjudicated similarity category. Reusable attack-roll, saving-throw, DC, damage-roll, and D20-modifier value objects capture only the mechanics that share the same behavior; specialized procedures such as Death Saving Throws retain their separate structure and XPHB Player Character eligibility. Standard Cover records half and three-quarters numerical bonuses, Dexterity-save applicability, direct targeting, and the most-protective-degree rule; total Cover is represented as a targeting restriction without damage reduction. Optional DMG Flanking preserves miniature use, visibility and Incapacitated restrictions, square-grid and hex-grid positioning, size-dependent hex separation, and Advantage without computing encounter positions. Skill/ability variation preserves the DM's discretionary pairing and PHB examples. Ability-score rules use a finite score-band-to-modifier table. Proficiency rules distinguish bonus application and level/Challenge Rating progression, Expertise scaling, optional proficiency dice, multiclass level basis, skill proficiency, tool/skill synergy, and the DMG Ability Check Proficiency variant. Passive scores state a base of 10, add the related check bonus, and preserve the source's +5/−5 Advantage/Disadvantage adjustments. Finite DC values reuse the shared typed `difficultyClass` union; a DM-selected DC remains distinct from a formula. Initiative procedures now distinguish Initiative score construction and Advantage/Disadvantage adjustments from side-based unmodified d20 ordering, ties, and within-side order. Carrying capacity uses finite Strength and size multipliers; optional encumbrance records strict-above thresholds and their penalties without computing a creature's carried inventory. Rest and recovery procedures preserve duration, permitted activity, start eligibility, interruption outcomes, recovery amounts, and source-defined variants. Damage Resistance and Vulnerability encode their respective halving/rounding-down and doubling operations and their once-per-damage-instance rule. These declarations describe mechanics and do not calculate a character's current values. The repeatable Core Rules validator checks local component references, compatible applicability targets, contradictory OR branches, and cyclic dependencies in addition to schema validation.

Disease records use bounded disease-specific structures rather than a general effects language. Incubation and progression distinguish fixed or randomized onset, elapsed time, dawn, Long Rest completion, symptom onset, and turn or damage events. Saving-throw branches carry separate success and failure outcomes, condition/DC termination, and source-scoped outcome counters. A counter can preserve consecutive, independent, or source-unspecified sequence/reset behavior; unspecified reset behavior is not an executable default. Exposure procedures retain route, source creature or material, target applicability, exclusions, saving throw, and scoped immunity. Typed effects cover the observed disease mechanics, including condition changes, roll modifiers, damage vulnerability, recovery restrictions, timed conditions, and transformations. Disease-profile reuse is limited to explicit source-qualified component references. This does not imply a universal disease lifecycle or execution engine.

Sense `SIGHT` capabilities express dim-light and darkness transformations independently. `NONVISUAL_PERCEPTION` may specify a typed location precision, retaining the difference between pinpointing a vibration origin and pinpointing detected creatures or movement. Illusion interactions identify only source-supported automatic detection, transparency, or saving-throw outcomes; edition-specific capabilities remain separate records.

Rule records may carry the optional `ruleType` classification when the source supplies it: `C` maps to `CORE`, `O` to `OPTIONAL`, `V` to `VARIANT`, and `VO` to `VARIANT_OPTIONAL`. These are the only accepted values; an absent source classification remains absent. Language scripts remain useful string values on Language records. The source's LanguageScript records contain font paths and no other relevant canonical information, so no LanguageScript model is defined.

Language speaker filters preserve creature types and exact source tag selectors as distinct criteria; tags do not imply creature types, and an explicitly supplied source scope is retained. Search-based selectors with unresolved matching semantics are not executable canonical selectors. Language can declare a bounded concealed-message channel, knowledge requirement, source-defined detection or deciphering limits, and communication-time multiplier. A typed mutual-intelligibility relation records communication mode and direction. These declarations do not implement creature-tag search, perception execution, spell resolution, inscription state, or language acquisition.

Condition mechanics use bounded, typed effects whose actors and related creatures are expressed as roles, not canonical creature identities. Applicability predicates cover source-supported relationships, including fear-source line of sight, charmer social interaction, observer visibility, creature distance, and attack-target identity relative to the grappler. Activity restrictions distinguish Actions, Bonus Actions, Reactions, speech, and movement. Condition interactions state whether an applied Condition exists only while its source Condition is active or persists independently; immunity is a separate interaction. Movement constraints and the grappler's voluntary drag/carry cost remain distinct from forced movement. A `CRITICAL_HIT_ON_HIT` outcome requires a successful hit and five-foot attacker distance; the Critical Hit Rule continues to define critical-hit resolution and damage. PHB Petrified separately declares suspension of existing Disease instances while the Condition remains active. The declaration preserves the Disease instance and leaves timer scheduling and resumption timing unresolved where the source does not specify them; it does not mean immunity to new infection or cure.

## Interpretation boundaries

Mechanics are domain-specific. These contracts do not define a universal effect engine or a prose fallback. A contract's enumerated mechanics encode only supported structures; an unrepresented mechanic is kept out of canonical JSON and accounted for in the external omission register, with complete source identity and original entry content. If part of an entry is supported, retain the typed portion and document the complete entry and unsupported portion in that register. Duplicate source content is recorded separately with its complete content and identity.

The Action, Condition, Disease, Rule, Sense, and Status schemas are intentionally explicit and do not cover every source mechanic. Complex disease transformations, optional Rule subsystems, ship and campaign procedures, exceptional Condition interactions, and novel sensory mechanics can require further reviewed contract design. Creature-specific sense ranges and many cross-domain references are resolved only when their target domains are available. Structural schema validation does not prove the mechanical interpretation is correct.

## Schemas and examples

Each model schema is stored at `src/main/resources/schemas/<model>/schema.json`; the shared schema is at `src/main/resources/schemas/common/schema.json` and defines identity, source metadata, references, ability names, actor roles, typed Action triggers and conditions, timing, and reusable mechanical values. `npm run validate:core-rules` compiles the Draft 2020-12 schemas, validates all canonical Core Rules records, checks cross-component integrity, and runs positive and negative contract checks. Separate schema example files are not maintained; the canonical records are the validation data.

The Phase 2 design feedback and validation history are maintained in the [Core Rules Phase 2 report](../reports/step-2/CORE_RULES_FOUNDATION_PHASE_2_SCHEMA_VALIDATION.md); execution findings belong in reports rather than this system contract document.

Rule movement mechanics use bounded `MOVEMENT_SPATIAL` components. They describe movement costs, traversal prerequisites, finite jump procedures, special-Speed selection, fall triggers, and flying exceptions without assigning Speed values to creatures or executing movement. Difficult Terrain remains non-cumulative with other movement surcharges where its source says so. Grid rules describe the source-defined movement units and costs; they do not resolve paths, occupied spaces, corners, or range.

Area geometry reuses a single typed component family for the six XPHB shapes and the general Area of Effect procedure. Shape records specify effect-defined dimensions, source-defined origin placement and inclusion, and Emanation origin behavior. The general procedure records line-of-effect blocking by Total Cover and the near-side placement of an unseen origin beyond an obstruction. These fields do not enumerate targets or calculate a spatial intersection.

The XGE Falling Rule preserves the standard 1d6-per-10-feet bludgeoning procedure, the 20d6 cap, and the Prone landing consequence. Partial ten-foot increment treatment remains source-unspecified. Optional high-altitude timing and special falling variants are not included in that standard procedure. XPHB Flying retains its own condition triggers and Hover exception as a separate edition-specific Rule.

## Backend catalog integration

The backend packages consolidated, unversioned canonical domain arrays as classpath resources under `data/core-rules/`: `actions.json`, `conditions.json`, `diseases.json`, `languages.json`, `rules.json`, `senses.json`, `skills.json`, and `statuses.json`. `source-identities.json` indexes pinned source targets for reference handling. The deterministic aggregation command `npm run aggregate:core-rules` produces these application resources from the validated Phase 3 and Phase 5 datasets; `npm run validate:core-rules` verifies exact record equality, identity uniqueness, and source-index consistency. Individual conversion files remain review artifacts, not the runtime layout.

The shared `CoreRulesRepository` loads all eight datasets at startup and checks record identity/provenance, duplicate identities, and source-backed references. Separate domain repositories and services provide Action, Rule, Condition, Disease, Language, Skill, Sense, and Status access; each domain has its own read-only controller under `/api/core-rules/<domain>`. Identity lookup uses `GET /api/core-rules/<domain>/{source}/{slug}`. Reference resolution is exposed at `GET /api/core-rules/references/resolve?targetType=...&id=...` and distinguishes canonical targets from source-known identities without canonical outputs and unknown identities. The Skill, Language, Sense, and Status endpoints use schema-shaped Java DTOs and preserve canonical JSON through Jackson round-trips. Action, Rule, Condition, and Disease endpoints currently return their validated canonical records unchanged while their schema-union DTOs remain under implementation. JSON Schema validation remains authoritative offline; Java performs startup integrity checks. Runtime services do not interpret source prose or execute mechanics.
