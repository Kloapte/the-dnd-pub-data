## Typed selected-target count

The new `SelectedTargetCount` payload value holds `maximumSelectedTargets: 5`. Its semantics couple
the number of attacks directly to the number of selected targets, with exactly one attack for each
selected target. It has no minimum field, and the attack claim has no fixed `attackCount`, character
level progression or slot progression. In JSON, `attackCount` is omitted for this mode. Existing
attack claims retain their integer count and their prior serialized form.

The attack context is `MULTIPLE_TARGET_CREATURES` with `maximumTargets: 5`. Its per-instance
allocation specifies exactly one source-supported `CREATURE` target, `DISTINCT_TARGETS_ONLY`,
visibility to the caster, and spell range. Document validation ties the target maximum to
`SelectedTargetCount.maximumSelectedTargets`; the attack model rejects a fixed count, level
progression, reused targets, missing visibility/range constraints, and non-creature eligibility in
this mode. The target-count type expresses “up to five”; it does not serialize a source-authored
minimum of one.

`AttackRollMechanic` gained an optional `SelectedTargetCount` field and nullable fixed `attackCount`.
The existing integer constructors and positive-count validation remain for all previously modeled
attacks. `MechanicsDocumentValidator` now recognizes a multiple-creature target subject as
CREATURE-eligible and enforces that its maximum equals the selected-target count. The shared pattern
registry includes a package-private `XgeSteelWindStrikeRules`; the XGE source-edition manifest pins
the resource fingerprint. These are source-bounded mechanics changes; no public REST projection or
general execution layer was added.
