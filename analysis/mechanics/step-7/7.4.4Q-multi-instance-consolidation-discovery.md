## 2. Consolidation review

### Current representation

| Model | Current responsibility and evidence | Assessment |
| --- | --- | --- |
| `AttackRollMechanic` | Attack kind, actor, base `attackCount`, independence, activation timing, optional `InstanceCountProgression`, optional `InstanceTargetAllocation`. | Appropriate for one or more attack rolls. `attackCount` serves as the base count when a progression exists; that is semantically sound but less explicit than a name such as “base count.” Renaming would change serialized contracts and is not warranted here. |
| `DamageMechanic` | One damage amount/type, optional `CharacterLevelDamageScaling`; its context carries the trigger and revision-bound relationship. | Correct for damage associated with an attack roll. Do not fold attack count into damage scaling: Eldritch Blast increases beams, not each beam’s 1d10. |
| `DamageInstanceSeriesMechanic` | Damage amount/type per instance, slot instance count, target allocation, resolution mode, timing, and roll grouping. | A distinct family is justified for Magic Missile: it has no attack roll, and each dart is assigned independently. It does not duplicate `DamageMechanic`’s hit-bound role. |
| `InstanceCountProgression` | Sealed union of `CharacterLevelInstanceCount` and `SpellSlotInstanceCount`. | Cohesive shared slot; the concrete progressions retain different level semantics. Do not merge character level and slot level into an untyped generic scale. |
| `CharacterLevelInstanceCount` | Ordered total-instance tiers; attack payload supplies the base count. | Validates nonempty, increasing thresholds and totals. Tier totals are not increments. |
| `SpellSlotInstanceCount` | Base spell-slot level, base instance total, positive instances added per slot level; computes totals only from the base level through 9. | Correctly distinct from cantrip damage scaling and protects calculation from integer overflow. It does not itself prove that an owner has a higher-level slot rule; evidence and extraction do that. |
| `InstanceTargetAllocation` | Per-instance cardinality, eligible categories, reuse rule, range flag, optional category-assessment state and typed requirements. | Reuse supports repeated or distinct targets. It is not a selected-target list and does not fabricate runtime target identities. The same type is useful on attack and automatic-hit series payloads. |
| `TargetCategoryEligibilityStatus` | `SOURCE_SPECIFIED`, `UNSPECIFIED_IN_SOURCE`, `NOT_ASSESSED`. | Properly distinguishes Scorching Ray’s unknown category from a positive category list. Legacy allocations can omit the status; this preserves their established serialization but leaves status implicit for old payloads. New source-unknown interpretations should continue to set the explicit state. |
| `AppliesOnAttackRollOutcome` | One effect references one attack claim revision and HIT/MISS outcome. | Correct for a single attack’s branch, including Inflict Wounds. It is not a per-instance binding. |
| `AppliesOnEachAttackRollOutcome` | Damage claim references one attack revision and an outcome scoped to the corresponding independent instance. | Correctly prevents one beam’s hit from triggering another beam’s damage. Validator checks same owner, claim kind, current revision/hash, independent attacks, damage payload, and common target subject. Dependencies are one-way from effect to trigger. |
| `DamageResolutionMode`, `EffectTiming`, `DamageRollGrouping` | Explicit automatic-hit resolution, simultaneous timing, and damage-roll grouping state. | Typed fields preserve Magic Missile semantics and the unresolved roll grouping. Their current enums have one value each; that is not a reason to replace them with strings or generic properties. Add values only when source-supported semantics require them. |

Evidence remains associated to the claim paths that each source fact supports. Source artifact
revisions are validated against the owner document; evidence hashes are checked; stable claim IDs,
revisions and `MechanicRevisionReference` content hashes protect dependencies. Review, licensing and
publication authorization remain separate metadata and gates.

### Defects versus future guardrails

No defect was found that requires consolidation before further extraction. The distinctions between
attack rolls and automatic-hit damage, attack count and damage amount, character-level and slot-level
progression, and explicit versus unspecified target categories are meaningful domain boundaries.

The following are future guardrails, not reasons to rewrite the pilots:

- `InstanceTargetAllocation` permits a category list with no explicit assessment enum for legacy
  compatibility. New constructors and extraction rules should prefer an explicit status where source
  certainty matters; a migration would change old serialization and is not proposed.
- `AttackRollMechanic.attackCount` is the base count when count progression is present. Document this
  invariant in future model APIs instead of renaming the serialized field.
- Target cardinality is validated against the Spell target subject, but future variable-count attacks
  need a typed link between the selected distinct target count and the number of attack instances.
- `DamageInstanceSeriesMechanic` currently intentionally covers automatic-hit simultaneous instances.
  Do not broaden its enums speculatively to make it a generic damage scheduler.
- The generic inventory reason arrays do not explain every `PARTIALLY_SUPPORTED` row. This is a
  reporting traceability gap, not a reason to rewrite coverage status in this analysis.

## 4. Corpus-wide discovery methodology and counts

The screening pass parsed all 18 `src/main/resources/data/spells/spells-*.json` resources in the
pinned 5eTools v2.37.0 corpus. It traversed authored `entries` and `entriesHigherLevel` strings and
cross-checked structured `spellAttack`, `damageInflict`, `scalingLevelDice`, `miscTags`, `target`,
`range`, `time`, and `duration` fields. The pattern screen selected 170 distinct source-aware owners
out of 969 for manual triage. Overlapping keyword-screen counts were:

| Screened authored wording | Distinct source-aware owners | Why this is only a lead |
| --- | ---: | --- |
| Number + ray/beam/dart/missile/projectile/mote/stone | 7 | Can refer to one visual effect or a fixed count without independent outcomes. |
| Separate/each/repeated attack wording | 12 | May describe a recurring action, creature action, or one attack against each selected target. |
| Automatic/automatically | 40 | Often means automatic saving-throw failure, forced movement, or an effect without a damage attack. |
| Simultaneous / same time | 12 | Can describe unrelated creation or duration events. |
| Attack hit/miss wording | 75 | Includes ordinary single attacks and area effects that occur on either result. |
| Additional projectile plus slot-level wording | 2 | A narrow lexical pattern; structured scaling and different authored phrasings can be missed. |
| Same/different/multiple selected targets | 16 | Does not establish a separate attack or damage instance per target. |
| Repeated turn / later-turn / bonus-action wording | 62 | Includes non-damage actions and persistent areas. |

Counts overlap and must not be summed. They describe the screening expressions, not verified mechanics
families or inventory support. The screen is intentionally recall-oriented and has both false positives
and false negatives; manual review of authored context, edition, action, target and outcome is required.
Structured tags alone were not treated as proof.

Source resources used for the detailed sample retain distinct PHB, XGE, TCE, AI and XPHB ownership.
No PHB interpretation below imports wording from XPHB. The selected entries provide architectural
variety across per-attack resolution, outcome branching, target allocation, finite spell-created
resources, ally attacks, repeated activations, and false positives.
