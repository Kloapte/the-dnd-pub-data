# 7.2.2 — Canonical mechanics values and independent review/rights metadata

Status: implemented and verified, 18 October 2026.

Architectural baseline: [7.2.1 model and API contract](7.2.1-mechanics-model-and-api-contract.md).
This batch adds passive internal Java values, validation and tests. It does not extract a mechanic,
register a mechanics catalog, change an existing definition or publish a new API property.

## 1. Packages and implementation boundary

- [`com.thedndpub.data.mechanics.model`](../../../src/main/java/com/thedndpub/data/mechanics/model/):
  128 files containing canonical records, sealed vocabularies, enums and integrity helpers.
- [`com.thedndpub.data.mechanics.review`](../../../src/main/java/com/thedndpub/data/mechanics/review/):
  nine files containing decisions, trusted caller policy, derived review states and aggregation.
- [Model tests](../../../src/test/java/com/thedndpub/data/mechanics/model/): four test classes and
  one fixture helper, with 64 new test executions.

One public top-level type is defined per file. Collections are copied with `List.copyOf` through
`ModelChecks.list`. Optional canonical collections equate omitted/null and empty lists so that
`NON_EMPTY` serialization round trips. Required alternatives, terms, evidence and rights coverage
have additional nonempty constraints. No source DTE presence semantics were changed.

The package boundaries follow 7.2.1. The model has no Spring component annotations, controllers,
repositories, mutable registries, P1D dependencies or source-to-mechanics mapper.

`NOT_ATTEMPTED` / `NOT_ASSESSED` is a valid empty document, distinct from a processed
`NONE_SUPPORTED` document with unsupported evidence. Failed/unattempted processing cannot claim
successful interpretations. Partial documents and partial individual claims remain representable.
`COMPLETE_WITHIN_SCOPE` requires no unassessed paths, no unsupported constructs, complete claims,
and no blocking review findings. This scoped completeness does not certify human correctness.

`MechanicsDocument` checks duplicate IDs, reference ownership, source/evidence fingerprints,
coverage totals, derived review summary and document content hash. An unsupported construct
requires evidence and can retain proposed alternative revision references without selecting one.

## 2. Initial payload vocabulary

`MechanicPayload` is sealed and has exactly seven implementations:

| Java record | JSON `kind` | Meaning of the value, without execution |
| --- | --- | --- |
| `ArmorClassModifierMechanic` | `ARMOR_CLASS_MODIFIER` | Signed or symbolic modifier; no AC calculation or stacking |
| `ReactionActivationMechanic` | `REACTION_ACTIVATION` | Reaction cost and ordered trigger expression |
| `EffectDurationMechanic` | `EFFECT_DURATION` | Duration specification or explicit reference |
| `SpellDamagePreventionMechanic` | `SPELL_DAMAGE_PREVENTION` | Spell-specific prevention claim, with an authored Spell mention |
| `DamageMechanic` | `DAMAGE` | Amount expression and damage-type selection, with context kept separately |
| `HealingMechanic` | `HEALING` | Amount expression and `RESTORE_HIT_POINTS` mode |
| `SavingThrowRequirementMechanic` | `SAVING_THROW_REQUIREMENT` | Ability selection and fixed or unknown difficulty |

These are proposed claims when constructed. Constructing a `DamageMechanic` does not establish
that a damage tag means applied damage; an adapter must supply effect-role evidence and context.
A wholly unknown damage amount and type belongs in unsupported constructs rather than a claim.

### Supporting values

| Area | Types and constraints |
| --- | --- |
| Modifiers | `ModifierAmount`, `IntegerModifier`, `SymbolicModifier`; an optional authored integer token must parse exactly to its value, retaining `+0`/`-0` |
| Amounts | `AmountExpression`, `IntegerAmount`, `DiceAmount`, `SymbolicAmount`, `SumAmount`, `UnknownAmount`, `AmountSymbol`; ordered sums are not simplified or evaluated |
| Triggers | `TriggerExpression`, `AnyTrigger`, `AllTriggers`, `HitByAttackTrigger`, `TargetedBySpellTrigger`, `AttackEventKind`, `ReactionActionCost` |
| Spell mentions | `SpellMentionReference`, `SpellMentionForm`, `MechanicsReferenceDisposition`; optional authored source qualification is distinct from a resolved target |
| Duration | `DurationSpecification`, `DeclaredSpellDurationReference`, `FixedDuration`, `UntilTurnBoundary`, `ReferencedDuration`, `UnknownDuration`, `DurationUnit`, `TurnActor`, `TurnBoundary` |
| Damage types | `DamageTypeSelection`, `FixedDamageType`, `DamageTypeChoice`, `UnknownDamageType`; exact authored codes and alternative order retained |
| Saves | `AbilitySelection`, `FixedAbility`, `AbilityChoice`, `UnknownAbility`, `Ability`, `SaveDifficulty`, `FixedSaveDifficulty`, `UnknownSaveDifficulty`, `SaveOutcome` |
| Subject | `SubjectReference`, `CasterSubject`, `UnknownSubject`, `UnknownValueReason` |
| Context | `MechanicContext`, `MechanicContextBinding`, `ActivatedBy`, `AppliesForDuration`, `AppliesOnSaveOutcome`, `IncludesTriggeringAttack` |

`ATTACK_HIT` and `ATTACK_ROLL_HIT` are distinct event kinds for the PHB/XPHB wording distinction.
ANY/ALL grouping, trigger order and authored source qualifiers are retained. No trigger is evaluated.
Resolved Spell mentions require explicit tagged-reference form, a target ID and resolution evidence
fingerprint. Plain prose does not acquire a target ID. This model creates no resolver occurrences.

`DiceAmount` keeps count, sides and signed modifier; the original formula syntax stays in the
referenced observation/evidence. Symbolic values identify a variable without calculating its value.
`UnknownAmount` is different from zero. Unknown subject, ability, damage type, DC and duration are
explicit values with reasons. An absent optional qualifier is not replaced with an invented value.

Context bindings carry evidence IDs and exact referenced mechanic revisions. Their evidence must
also appear in the claim's fingerprint-bound associations. A save outcome must reference a save
requirement, activation a reaction activation, and a duration reference an effect-duration claim.
Missing/stale references create review findings; they are never silently rebound to a new revision.
Rejected or review-blocked dependencies propagate a review finding to consumers deterministically.

## 3. Evidence and provenance

`MechanicsEvidence` is a sealed hierarchy:

| Type | Preserved evidence |
| --- | --- |
| `TextMechanicsEvidence` | Existing Batch 5 `SyntaxEvidence`, original resource fingerprint, JSON Pointer, hierarchy and UTF-16 `[start,end)` span; text fingerprint and source reference |
| `StructuredFieldMechanicsEvidence` | Existing `SyntaxSourceOwner`/`SyntaxContext` hierarchy, original field pointer, structured-value fingerprint and source; **no text span** |
| `TransformedMechanicsEvidence` | Effective owner/pointer, output fingerprint, pinned input evidence references and ordered transformation instructions; **no fabricated authored output span** |
| `UnavailableOriginMechanicsEvidence` | Effective owner/pointer/value fingerprint and explicit reason; no fabricated original locator |

Additional types: `MechanicsOrigin`, `MechanicEvidenceAssociation`, `EvidenceRole`,
`EvidenceRevisionReference`, `MechanicsTransformationReference`.

Text/field origins distinguish `AUTHORED` and `INHERITED_UNCHANGED`. Inherited evidence requires
its original authored owner; a document may have a different effective owner. Original syntax
locations remain authored locations. Transform inputs must exist with exact matching evidence
hashes; instruction evidence must be among those inputs. Cyclic transformation lineage is rejected.
Unavailable origin, including through transformed inputs, prevents effective verification while
retaining the historical human decision.

Evidence associations point to an actual `/payload` or `/context` claim path. An `EFFECT_ROLE`
association must address `/payload`, rather than implying that a formula alone establishes the
effect category. Field and context associations can address specific nested paths.

### Observations remain separate

`MechanicsObservationReference` has three variants:

- `FormulaObservationReference`: Spell ID, existing occurrence index, pinned source artifact and
  original Batch 5 evidence, joining the Batch 6 index without duplicating formula interpretation.
- `StructuredDeclarationReference`: normalized property, source artifact and original field pointer.
- `OtherSyntaxObservationReference`: syntax evidence and tag name, without effect semantics.

Observation IDs and content fingerprints are pinned in derivation metadata. Pool membership does
not convert an observation into a claim. Repeated occurrences retain distinct locators/indices.

### Integrity checks versus source validation

The records validate shape, ownership, paths, hashes and joins; they do not read prose or prove
that a supplied pointer's content supports an interpretation. A future adapter must verify actual
source values/spans before constructing evidence. `MechanicsSourceValidation` checks canonical
source-registry references. `MechanicsCatalogValidation.validateSpell` explicitly checks the
authoritative existing Spell owner/source, formula occurrence/evidence and declared duration index.
These are read-only helpers, not startup indexes or interpreters. Other catalog adapters need their
own authoritative joins before materializing mechanics; non-Spell owner namespaces are checked
against their domain prefix without guessing other catalogs' identity dialects.

## 4. Stable identities and revisions

Example IDs:

```text
mechanic:spell:phb:shield:ac-bonus
mechanic:spell:xphb:shield:ac-bonus
```

`MechanicId.of(owner, stableSlot)` requires an explicit stable claim slot. Callers must maintain
that slot across substantive revisions; values, filtered positions, review/rights states and
cross-source name similarity do not establish identity. PHB and XPHB owners remain distinct.

Claim hash protocol v1 is SHA-256 over deterministic Jackson serialization of
`MechanicRevisionContent`: ID, payload, context, evidence associations, derivation and assessment.
Properties are sorted for hashing; list order remains substantive. The codec and hash mapper are
local to this library and do not modify application Jackson configuration.

Two implementation refinements make the approved evidence/revision design enforceable:

1. `MechanicEvidenceAssociation` includes the associated evidence's `evidenceSha256`.
2. Derivation includes pinned `sources` and fingerprinted `ObservationRevisionReference` inputs.

This binds original source revisions, evidence locations, context and inputs without copying full
source entries into every claim. Changing any of them changes the claim hash. A stale serialized
hash is rejected. Review and licensing decisions do not change the substantive claim hash.
Assessment changes do require a new claim revision, so an old decision cannot certify a newly
expanded scope or changed benchmark evidence.

First revisions omit supersession. Later revisions identify their exact immediately preceding
revision, including ID, number and hash. Document revisions separately bind the full joined
snapshot, including review/licensing metadata, excluding the document's own revision field.
There is no database, history ledger or automatic continuity matching. Future persistence must
retain predecessor snapshots and increment document revision numbers when snapshots change.

## 5. Human review and deterministic assessment

Review package types:

- `MechanicsReviewStatus`: `PENDING_REVIEW`, `NEEDS_MECHANICS_REVIEW`, `VERIFIED`, `REJECTED`.
- `HumanMechanicsReviewDecision`, `MechanicsReviewAction`, `MechanicsReviewerAuthority`.
- `MechanicsReviewPolicy`, `ValidatedHumanMechanicsReview`, its dedicated deserializer.
- `MechanicsReviewState`, `MechanicsReviewSummary`.

A decision records its ID, exact claim revision, reviewer, authority reference, action, rationale,
UTC review timestamp, explicit partial-scope acceptance and optional superseded decision ID.
Timestamps use validated ISO UTC strings, consistent with the existing publication records;
no new Jackson time module or application configuration is required.

`ValidatedHumanMechanicsReview.validate` requires a matching trusted caller-supplied reviewer
mandate. Deserializing a decision also requires that policy through Jackson context attributes;
an interpretation's JSON cannot configure its own policy. `MechanicsJson.mapper()` has **no trusted
reviewers** by default. No production mandates or decisions were seeded. This is an explicit
backend trust boundary, not authentication, identity proof or persistence. A future review service
must supply authenticated human decisions and preserve their history.

Recorded and effective statuses differ:

- Without a validated human decision, recorded status is pending.
- Only an exact-current-revision human `VERIFY` can produce effective `VERIFIED`.
- Missing essential evidence, unknown essential values, unresolved references, unavailable origin,
  contradictions, failed benchmarks and stale/rejected dependencies require review even if a prior
  human decision says verified.
- A human can verify a bounded partial claim only with explicit partial-scope acceptance and no
  essential blockers. This never changes its `PARTIAL` completeness.
- Applicable rejection remains rejected. A decision for an old revision remains recorded but is
  effectively review-required. The original decision is retained.
- Benchmark success alone never verifies a claim; benchmark failure blocks verification.

The canonical JSON stores the decision and findings, not an authoritative `effectiveStatus` value.
`recordedStatus()` and `effectiveStatus()` are derived methods. A JSON-supplied status flag is an
unknown field and is rejected by the strict codec. 7.2.3 must explicitly project computed statuses.

Findings use typed codes/severity and evidence references. Correctness blockers cannot be downgraded
to informational findings. Diagnostics inspect typed values and relationships only; they do not
parse source text, score natural language or assign confidence percentages.

`MechanicsReviewSummary.from` counts every individual effective state. Empty documents have zero
counts and no aggregate status. All verified/rejected produce the corresponding aggregate; any
review-required state or a mixture containing rejection produces `NEEDS_MECHANICS_REVIEW`;
otherwise outstanding pending decisions produce `PENDING_REVIEW`. A supplied inconsistent summary
is rejected. Individual states remain available and are not replaced by the aggregate.

## 6. Rights metadata and P1D separation

`MechanicsLicensing` variants:

| Variant | Status | Required basis |
| --- | --- | --- |
| `UnassessedMechanicsLicensing` | `NEEDS_REVIEW` | Default; may retain partial coverage and prior determinations |
| `SrdMechanicsLicensing` | `SRD` | Specific SRD document/version, license, claim-scoped evidence, decision and attribution references |
| `OtherMechanicsLicensing` | `LICENSED` | Specific licensed document, license/permission, claim-scoped evidence, decision and attribution references |
| `OpenMechanicsLicensing` | `OPEN` | `EstablishedReuseBasis` with whole-claim scope, evidence and decision reference |

Supporting records: `ClaimRightsScope`, `LicenseCoverage`, `LicensedDocumentReference`,
`LicenseReference`, `RightsEvidenceReference`, `RightsDecisionReference`, `AttributionReference`,
`EstablishedReuseBasis`; enums `MechanicsLicensingStatus`, `LicensingReviewReason`.

Whole-claim classification requires coverage of both `/payload` and `/context`, bound to the exact
claim revision. Token-only coverage is retained under `NEEDS_REVIEW` and cannot establish SRD or
LICENSED status for the full interpreted claim. Established stale classifications revert to
`NEEDS_REVIEW`, retaining the previous determination. Current licensed variants conservatively
require attribution configuration references; future permissions with different notice obligations
need separately designed coverage rather than fabricated notice evidence.

These records require documented references; they do not independently verify legal truth or grant
publication permission. No status is inferred from numeric values, source names, source flags or
extraction reliability. No rights classification grants mechanics verification. No mechanics
verification grants rights clearance.

P1D is neither imported nor consulted. There are no publication filters in document construction,
review or serialization. Private inspection is not blocked by `NEEDS_REVIEW`; eventual external
publication must use its separately approved authorization/projection policy.

## 7. Serialization contract

- Sealed payload, value, evidence, context and observation hierarchies use explicit stable `kind`
  discriminators with declared subtypes. No class-name discriminator or global default typing.
- Rights use the approved 7.2.1 `status` discriminator (`SRD`, `LICENSED`, `OPEN`, `NEEDS_REVIEW`),
  independent from review and effect-kind discriminators.
- Canonical records use `@JsonInclude(NON_EMPTY)`; optional absent fields/lists are omitted.
  Required primitive fields use `@JsonProperty(required = true)`. Numeric zero and Boolean false
  remain meaningful and round trip; unknown values have explicit kinds/reasons.
- `MechanicsJson` supplies a fresh strict opt-in mapper. Unknown properties/discriminators,
  duplicate keys, trailing values, null/missing required primitives, fractional integer coercion
  and numeric enum coercion are rejected. No global application mapper changes.
- Typed model round trips retain list ordering and immutable collection behavior. Hash serialization
  has a documented v1 field/order policy; future schema changes need explicit revision migration.
- The internal model is not a REST DTO. Audit decisions, provenance and evidence must pass through
  a deliberate 7.2.3 projection before any response changes.

## 9. Deferred functionality and 7.2.3 requirements

Not implemented: source interpretation, Shield extraction, effect execution, AC/bonus calculations,
formula evaluation, selection/eligibility inference, reviewer authentication, source upgrades,
persistence/history storage, external publication, REST inspection or frontend integration.

Only caster/explicitly unknown subjects are materialized now. Target selectors, referenced subjects,
areas, concentration effects, scaling effects, conditions, resource engines and other future payload
families need separate evidence-backed batches. Existing normalized Spell duration/scaling and
formula observations remain authoritative; this library does not extract duplicate values.

For separately authorized 7.2.3:

1. Keep ordinary responses, summaries, constructors and P1A formula statuses compatible. Add the
   approved opt-in `include=interpretedMechanics` detail/by-name projection separately.
2. Join existing source-aware Spell IDs and sources; call the explicit authoritative catalog/index
   validations. Do not match by name or manufacture origin spans for copied/transformed content.
3. Before interpretation exists, return honest `NOT_ATTEMPTED` / `NOT_ASSESSED` envelopes. A syntax
   observation is not an interpreted effect and does not imply complete coverage.
4. Project individual computed recorded/effective review states, independent rights, scoped coverage
   and bounded evidence references. Do not serialize whole source entries or the raw audit model as
   a shortcut. Backend review policy must not be accepted from request JSON.
5. Do not use P1D to suppress extraction/private inspection; do not treat SRD/OPEN or VERIFIED as
   publication permission. Preserve the zero-authorization release behavior until separately approved.
6. Add REST compatibility and omission tests without starting the 7.3 interpreter or benchmark suite.

7.2.2 is complete. 7.2.3 and every later batch remain unstarted.
