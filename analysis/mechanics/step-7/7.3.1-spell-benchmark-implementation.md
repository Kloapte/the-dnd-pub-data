# 7.3.1 — Spell benchmark fixtures and validation harness

Status: implemented and verified, 18 October 2026. No interpreter or production interpretations are added.
The [roadmap](../../../docs/THE_DND_PUB_BACKEND_ROADMAP.md) remains authoritative.

## 1. Boundary and architecture

The isolated [benchmark package](../../../src/main/java/com/thedndpub/data/mechanics/benchmark/)
accepts a versioned fixture, an existing canonical `MechanicsDocument`, a declared extraction scope
and an evaluation mode. It has no Spring component, controller, catalog registration, P1D lookup,
source-to-mechanics adapter or source mutation. Existing canonical, inspection, normalization,
public API and publication types are unchanged.

The [fixture index](../../active/mechanics/benchmarks/README.md) locates the six test resources and
review procedure. The schema is a strict Java record graph, reusing canonical sealed payloads,
subjects, durations, evidence, source revisions and enums. There is no generic effect dictionary,
new canonical family or parallel source identity. Source-tree reads are limited to offline fixture
authoring/validation; they do not populate an interpretation or run in HTTP requests.

### Types

| Concern | Types |
| --- | --- |
| Schema/content revision | `SpellBenchmarkFixture`, `FixtureContent`, `FixtureRevision`, `BenchmarkFixtures` |
| Expected claims | `ExpectedMechanic`, `ExpectedContext`, sealed `ExpectedBinding` with `ExpectedActivation`, `ExpectedDuration`, `ExpectedSaveOutcome`, `ExpectedTriggeringAttack` |
| Evidence/syntax controls | `ExpectedEvidence`, `ExpectedFormula` |
| Negatives/abstentions | `BenchmarkProhibition`, `ProhibitionRule`, `DeferredExpectation` |
| Human fixture review | `FixtureLifecycle`, `FixtureReview`, `BenchmarkHumanDecision`, `BenchmarkReviewerAuthority`, `BenchmarkReviewPolicy` |
| Scope/evaluation | `ExtractionPattern`, `ExtractionScope`, `BenchmarkMode`, `SpellMechanicsBenchmark`, package-private `BenchmarkSemantics` |
| Reporting | `BenchmarkReport`, `BenchmarkClaimResult`, `BenchmarkPatternResult`, `BenchmarkMetric`, `MetricAvailability`, `BenchmarkRunState` |

Records defensively copy collections. Fixture fingerprints bind the entire substantive schema,
owner/source, locators, expectations, constraints and negative rules. Human decisions are separate
from that content hash and bind both the numbered fixture revision and source fingerprint.
Duplicate expected keys, invalid dependency families and cycles are rejected. Evidence association
paths use existing canonical validation. Unknown JSON fields, versions and discriminators fail closed.

## 3. Proposed Shield expectations

Both sources have five proposed claims, separately authored and separately fingerprinted:

| Fixture key / extraction pattern ID | Proposed assertion and source evidence |
| --- | --- |
| `activation` / `shield-reaction-v1` | One reaction from `/time/0/number` and `/time/0/unit`; ordered alternatives from `/time/0/condition` |
| `ac-bonus` / `shield-ac-v1` | Integer modifier `5`, authored token `+5`, caster subject; activation, prose duration and triggering-attack inclusion bindings from `/entries/0` and the reaction condition |
| `structured-duration` / `spell-declared-duration-v1` | `DeclaredSpellDurationReference` to duration index 0; actual `/duration/0` is timed, one round. Self range separately supports subject metadata |
| `turn-boundary` / `shield-turn-boundary-v1` | `UntilTurnBoundary(CASTER, START_OF_NEXT_TURN)` from its exact prose span; not equated to the structured round declaration |
| `magic-missile-protection` / `shield-special-interaction-v1` | Narrow `SpellDamagePreventionMechanic`, caster subject, activation and turn-boundary context; spell mention comes from its exact authored body tag |

PHB's hit alternative is `ATTACK_HIT`. XPHB's is `ATTACK_ROLL_HIT`. Their second alternative is
Magic Missile targeting. PHB's trigger is an unqualified tag; XPHB's is a prose mention with **no
authored source qualifier**. XPHB's body tag explicitly qualifies the protected spell as XPHB;
PHB's body tag does not qualify its source. Neither fixture invents a resolved target ID.
Authored name spelling and trigger order are preserved. These distinctions are tested separately.

The AC includes the triggering attack where the body explicitly establishes that relationship.
The prevention claim is spell-specific, not general force immunity, blanket immunity or an attack
negation guarantee. Proposed evidence supports the bounded context, but a human must adjudicate
the interpretation before approving it. No actual Spell claim is VERIFIED by these fixtures.

Negative rules reject invented saving throws, damage effects, unsupported resolved references,
cross-edition evidence and any unmatched claim. An incorrect final-AC value, invented target/trigger
or lost qualifier does not match the bounded +5 claim. General immunity, calculated final statistics
and effect execution have no permitted canonical payload here; unknown kinds also fail parsing.
The negative guards do not pretend to interpret arbitrary prose errors or nonexistent payload kinds.

## 4. Other controls and model limits

- **Fireball:** proposed partial Dexterity-save requirement with unknown authored DC and a partial
  `8d6` fire damage claim on failure, linked to that save. Target identity remains explicitly unknown.
  Successful-save half damage, target/area constraints and slot scaling are deferred. The base
  `damage` token and higher-level `scaledamage` token are syntax controls, not complete effects.
- **Healing Word:** proposed partial healing amount sums `1d4` with the symbolic caster spellcasting
  ability modifier. Visibility, target choice, range, creature exclusions and slot scaling remain
  deferred qualifiers. Omitting the symbolic term is incorrect. `dice` and `scaledice` are controls.
- **Magic Missile:** one formula control; **no fabricated DamageMechanic**. Per-dart ownership,
  three initial darts, simultaneous distribution and one extra dart per higher slot level are
  separately reviewable deferred concepts. A dice token is not the whole spell effect.
- **Prestidigitation:** six ordered alternative-effect expectations, a limit of three simultaneous
  non-instantaneous effects and dismissal as an action. All eight remain unsupported concepts;
  no effect or player selection is manufactured.

Existing canonical types represent the selected partial claims. They do not yet express complete
target selection, areas, relative half damage, per-projectile quantities, executable scaling, effect
choices or dismissal/resource state. Those portions stop at evidence-backed deferred expectations;
this batch does not expand the canonical model. Human adjudication remains necessary for all six
fixtures, including whether the deliberately partial future controls are the right extraction scopes.

## 5. Semantic comparison and metrics

Matching is not document JSON equality. Whole document revisions, review/rights metadata and local
evidence-pool IDs do not define semantic equivalence. Rules are explicit and deliberately strict:

1. Exact owner/source edition and source revision are mandatory.
2. Candidate assignments prefer exact payload **and context** in dependency order, followed by
   same-pattern/family near-matches for diagnostics. Every actual record can satisfy at most one
   expected claim. Fixture keys resolve relationships to actual, exact claim revision references;
   the extractor is not required to copy fixture slot IDs.
3. Typed payload values, authored tokens, subjects, ordered context bindings, ordered trigger
   alternatives and claim completeness must match. There is no formula evaluation, alias expansion,
   source inference, fuzzy span tolerance or post-hoc equivalence rule.
4. The declared scope is a list of `(family, patternId)` pairs. Missing in-scope claims are false
   negatives; extra eligible claims are false positives. Out-of-scope emissions are separately
   reported violations, not a way to hide errors by shrinking a denominator.
5. Evidence associations compare exact source/page, owner/resource/hash, JSON Pointer, hierarchy,
   origin, text/value hash, UTF-16 span, claim path and role. Binding evidence must also identify the
   correct actual binding. Local pool IDs can differ. Missing associations fail whole-claim evidence
   checks even when all supplied associations are individually correct.
6. An abstention requires a separately reported canonical unsupported construct matching the
   deferred family, reason and every required evidence locator. Silence is not credited. One
   unsupported construct cannot earn credit for multiple expectations. Missing supported claims
   and unexplained unsupported results are unjustified abstentions.

| Measure | Numerator / denominator or counts |
| --- | --- |
| Semantic precision | Correct eligible claims / asserted eligible claims |
| Semantic recall | Correct eligible claims / expected eligible claims; authoritative only after independent approval |
| Evidence accuracy | Correct supplied claim associations / all supplied claim associations; missing expected associations additionally fail per-claim evidence completeness |
| Abstention quality | Expected, explicitly honored, unreported/ambiguous and unjustified counts; separate from positive extraction |
| Completeness | Missing/incorrect qualifiers and claim completeness, false COMPLETE coverage, duplicate effects, scope violations and forbidden claims |
| Syntax controls | Exact observation-reference controls matched; excluded from semantic numerators/denominators |

Zero denominator means `NOT_MEASURED`, never 100%. Metrics retain integer counts rather than
inventing confidence percentages. Results include owner/edition, fixture revision, scope version,
deterministically ordered family/pattern groups and claim-level diagnostics. Negative guard counts
are rule violations: one bad claim can violate several guards, so they are not a semantic error rate.
Unjustified-abstention diagnostics count missing supported assertions and unmapped unsupported
records separately; these can describe overlapping errors and are not a count of unique Spells.

For this bounded fixture set, approved acceptance requires exact agreement on every in-scope
claim/evidence association, no extra/forbidden/duplicate/out-of-scope claims, correct coverage,
all mandatory abstentions and formula controls, and actual PROCESSED output. This is a labeled
fixture contract, not a corpus-wide statistical accuracy claim. Wider patterns require new,
independently reviewed and held-out cases. No arbitrary success percentage is introduced.

## 6. Independent review gate

Lifecycle: `DRAFT` → `PENDING_HUMAN_REVIEW` → explicit `APPROVED` or `REJECTED` decision.
Corrections produce a new numbered content revision and require a new decision; retain previous
decisions and disputes through Git history. No method turns a passing comparison into approval.

An approval requires an attributed reviewer, a separately configured authority/mandate, independent
review attestation, timestamp, rationale, decision ID, exact fixture ID/revision/content hash and source
fingerprint. JSON cannot configure its own authority. Unknown reviewers, stale decisions, missing
attestation, mismatched lifecycle, unknown decision values and changed fingerprints fail closed.
The policy is an explicit trusted-caller boundary, **not reviewer authentication or a signature
verification system**. Real attribution/independence must be established by the owner out of band.
No real review identities, dates, mandates or approvals are seeded.

- Candidate mode accepts only draft/pending fixtures, produces `CANDIDATE_DIAGNOSTICS`, and has
  `accepted = null`. Diagnostic ratios are not validated extractor accuracy.
- Approved mode requires an approved fixture whose review passes caller policy. Otherwise the
  invocation returns `NO_APPROVED_GOLD_SET`, NOT_MEASURED metrics and no acceptance, without
  substituting a pending oracle or failing Maven merely because approval is absent.
- Fixture review is independent of canonical mechanic review, rights and publication. A benchmark
  pass never changes a mechanic's review status or P1D authorization.

Before authoritative evaluation, follow the [review checklist](../../active/mechanics/benchmarks/README.md).
Synthetic approvals exist solely in unit-test memory and are never written to committed fixtures or
packaged resources. The positive test documents are comparator construction tests, not extracted
outputs or independent benchmark results.

The fixture loader joins each Spell to the existing authored-owner manifest and Batch 6 index.
It rejects duplicate fixture/owner IDs, missing owners, source/page/root/fingerprint mismatches,
missing fields, bad string/field hashes and invalid text spans. Every expected formula is checked
against its exact indexed occurrence, token and original source string. Text offsets are decoded
Java String UTF-16 `[start,end)`, with surrogate-pair boundary validation; structured nodes have
pointers and value hashes, never invented string offsets.
