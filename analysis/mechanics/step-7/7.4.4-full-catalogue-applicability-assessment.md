# Step 7.4.4 Full Spell Catalogue Applicability Assessment

**Assessment type:** read-only discovery. No new production extraction, canonical claims, adapters,
review decisions, licensing decisions, publication decisions, or authoritative inventory changes were
made.

## A. Executive summary

The pinned catalogue contains 969 source-qualified spell owners across 18 resources. The verified
production baseline is 129 processed owners and 840 not attempted. Existing production matchers
already run over all spell definitions at startup; therefore an unprocessed owner cannot be called
eligible under a current production predicate without contradicting the current pipeline baseline.
The number of additional owners safely eligible without code changes is **0 verified**.

A pre-existing, non-authoritative inventory assessment used a broader PHB-only candidate path and
recorded **48 unprocessed PHB owners with partial candidate claims**. Those candidates could reuse
existing interpretation code if production eligibility were expanded, but they are still partial,
owner-gated, not human reviewed, and not approved canonical interpretations. Another **55** unprocessed
PHB owners reached the inventory candidate adapter but produced no supported candidate claims and
need rule generalization or source-specific assessment. The remaining **737** owners are explicitly
undetermined. This is not a claim that they have no mechanics; lexical and structured signals alone
cannot establish semantics.

The distribution is:

| Primary owner classification | Owners | Share |
|---|---:|---:|
| `CURRENTLY_PROCESSED` | 129 | 13.3% |
| `EXISTING_RULE_ELIGIBLE` | 0 | 0.0% |
| `OWNER_OR_EDITION_GATED` | 48 | 5.0% |
| `EXISTING_RULE_NEEDS_GENERALIZATION` | 55 | 5.7% |
| `NEW_MECHANIC_FAMILY` confirmed | 0 | 0.0% |
| `AMBIGUOUS_OR_UNDETERMINED` | 737 | 76.1% |
| **Total** | **969** | **100%** |

The zero `NEW_MECHANIC_FAMILY` count is deliberate: this discovery pass did not equate a cue with a
mechanic. Unrecognized source structures remain undetermined until authored semantics are assessed.
Therefore this pass establishes that at least 5% of the catalogue has partial prior candidate output
behind a production gate, but it does **not** estimate the proportion the existing rules can fully
represent after review.

## B. Baseline, scope and method

Read the generic-first principle in [MECHANICS-MODEL.md](../../../docs/architecture/MECHANICS-MODEL.md#generic-first-spell-interpretation)
and the [7.4.4 architecture/pattern audit](7.4.4-generic-first-pattern-audit.md) first. The current
repository reports 8 top-level adapters, 4 cross-owner implementation units with limits, 6
single-spell adapters and 74 derivation-pattern identifiers. Derivation IDs remain claim-provenance
labels, not independent recognizers.

The deterministic [assessment script](assess-generic-first-catalogue.mjs) scanned all 18 pinned
`src/main/resources/data/spells/spells-*.json` files. It traversed the actual raw `spell` records,
retained source code and source-qualified ID, computed each resource SHA-256, and recorded owner
pointers `/spell/{index}`. It inspected schema fields from `SpellDte` such as identity, level, school,
time, range/distance, components, duration, mechanic tags, scaling, metadata and authored entries.
Nested `entries`/`entriesHigherLevel` strings were traversed recursively. Presentation/reference
metadata was not treated as a mechanic merely because it was present.

For the already-processed baseline and candidate results, the script joined the source owners to the
previously generated, non-authoritative preview:
`target/closure-inventory-preview-2/7.4.4A-spell-capability-inventory.json`. This preview was created
before this task; this audit did not rerun its candidate extraction. It is the source of per-owner
processing state and inventory-only candidate status, not a canonical interpretation registry.
`SpellMechanicsExtractionService` itself was not invoked by the assessment script.

The machine-readable JSON contains one sorted record per owner, the source revision/path/hash, source
pointers, current processing/coverage, prior inventory-only candidate family and diagnostics, and
separate structured-field and authored-text cue lists. Text cue spans are UTF-16 code-unit offsets
into the exact JSON string at the given pointer. These are discovery locators, not evidence
associations for mechanic claims. Cue rules deliberately have no numerical confidence score.

Owner categories were assigned conservatively:

- Processed rows are `CURRENTLY_PROCESSED`.
- Unprocessed rows with inventory-only candidate claims are `OWNER_OR_EDITION_GATED`.
- Unprocessed rows selected by the inventory candidate adapter but with no supported claims are
  `EXISTING_RULE_NEEDS_GENERALIZATION`.
- Remaining rows are `AMBIGUOUS_OR_UNDETERMINED`, even when they contain relevant fields or prose
  cues. Those cues are recorded as secondary, source-backed leads.
- No unprocessed owner was labeled `EXISTING_RULE_ELIGIBLE`: a production predicate match would
  already have been processed by startup extraction. No owner was labeled `NEW_MECHANIC_FAMILY`
  without semantic assessment.

This method verifies source pointers by constructing them from the actual loaded resource and array
index, checks every source-qualified identity against exactly one prior inventory record, checks
resource/source distributions, and rejects duplicate IDs or unmatched owners. PHB and XPHB are
distinct IDs and are never merged. The 175-resource hash verifier was run separately.

### Candidate cohorts from prior inventory output

The 48 partial candidate owners are all PHB and were returned by the inventory-only broadening of
`phb-damage-healing-and-conditions-v1`. Representative owners are `spell:phb:poison-spray`,
`spell:phb:blade-barrier`, `spell:phb:cloud-of-daggers`, `spell:phb:wall-of-fire`, and
`spell:phb:bestow-curse`. The prior candidate inventory contains the complete 48-owner list. Their
candidate claims do not imply full-spell accounting: additional mechanics remain partial or
unsupported, and every owner needs source review before any future production enablement.

The 55 rows classified `EXISTING_RULE_NEEDS_GENERALIZATION` were selected by the same broader
inventory adapter, but no supported claim was produced. Examples include `spell:phb:bigby-s-hand`,
`spell:phb:chromatic-orb` (the PHB identity), `spell:phb:animate-objects`, and
`spell:phb:alter-self`. Their indicators include unsupported save/damage families and ambiguous
condition interpretations. These are generalization leads, not proven matches to a current mechanic.

No unprocessed owner is currently verified as production-eligible with no code change. The 48
candidate claims indicate a possible rule-reuse cohort, but production matching is explicitly more
restrictive. Removing those owner gates would require a future code change and is not authorized by
this assessment.

  authored markup and mechanics must be assessed separately before reuse.

## G. Coverage opportunities and recommended cohorts

Ranked by direct evidence and likely reuse (not projected owner totals):

1. **Review the 48 PHB inventory-only candidate owners.** This is the strongest measured opportunity
   because the existing internal code already produced partial candidate claims. Start with a
   representative subset spanning a save/damage area, a single-target save effect, and a damage plus
   slot-scaling spell; examples include `spell:phb:blade-barrier`, `spell:phb:bestow-curse`, and
   `spell:phb:cloud-of-daggers`. Retain unsupported mechanics and assess the entire authored scope.
2. **PHB attack cohort after the 48 candidates:** compare source owners with the `spellAttack`
   structured field and attack/damage prose. The 65 structured and 107 lexical counts are candidate
   leads only. Sample one cantrip, one ordinary hit-damage spell and one spell with a rider or unusual
   target to test where generic attack rules stop fitting.
3. **PHB scaling comparison:** compare structured `scalingLevelDice` records and authored higher-level
   entries with existing slot and character-level progression types. The 41 structured / 383 lexical
   owner signals are not eligible-owner totals. Keep attack-count and damage scaling distinct.
4. **Cross-edition source-diverse cohort:** select one each from XPHB, XGE, TCE and AU only after
   source-specific prose and fingerprints are confirmed. Do not apply PHB extraction across source
   codes. XPHB `spell:xphb:chromatic-orb` and PHB `spell:phb:chromatic-orb` are a useful contrast, not
   a shared owner.
5. **New families only after recurrence evidence:** persistent activations, attack-triggered areas,
   object consumption and conditional chains already have typed models but owner-specific recognizers.
   Compare a source-diverse set before attempting reusable extraction. Cues such as “when,” “until,”
   “create,” or “attack” are too broad to establish common semantics.

For future progress, report independently: owners processed; owners with FULL_SPELL versus
DECLARED_SUBSET accounting; complete/partial claim counts and owner coverage; unsupported families
and source paths; human-review readiness and actual review decisions; licensing status; and publication
authorization. Do not collapse these into one “supported spells” number.

## H. Architecture obstacles

1. Six of eight registered adapters use exact spell-owner gates. The PHB broad adapter also contains
   static owner lists and specific text branches.
2. Every owner is checked at startup, but only against the current matcher set. Similar JSON tags or
   keywords do not create a new rule match.
3. The registry accepts zero or one top-level adapter per owner. Overlap fails; no rule precedence or
   multi-adapter composition plan exists. The PHB class composes helpers manually as an exception.
4. The offline inventory's PHB candidate eligibility is broader than production eligibility and is
   coupled to `supportsForInventory` / `extractForInventory`. It cannot be confused with runtime
   support or canonical production processing.
5. Text spans and structured evidence can be checked against pinned source bytes, but recognizing a
   mechanical relationship across nested entries still requires a source rule that identifies the
   right subject, timing, condition and outcome.
6. Full source accounting requires explicit path decisions. Merely scanning every field cannot prove
   that every mechanically relevant authored statement has been represented.
7. Current testing is strongest around the 7.4.4 pilot semantics and structural invariants. It does
   not establish human-reviewed correctness for all 279 claims or the 48 inventory candidate outputs.

## I. Verification and limitations

The deterministic script generated two previews under `target/generic-first-preview-1/` and
`target/generic-first-preview-2/`. Both machine JSON files and summary Markdown files were byte-for-byte
identical. The script asserts 18 source resources, 969 unique owner IDs, one-to-one owner joins,
source-count equality with the prior inventory, and 129/840 processed-state reconciliation. The
source JSON owner pointer is constructed from the actual resource array index; text cue pointers are
constructed while walking those source objects.

The existing verifier completed successfully:

```text
node analysis/mechanics/batch-11b-item-charge-syntax/verify-source-hashes.mjs
Verified 175 pinned source JSON hashes.
```

`git diff --check` passes. No Maven tests were run because no production code, tests, models or
authoritative data were changed. The classifications are an applicability assessment rather than a
rules adjudication. In particular, the 48 candidate claims come from a prior inventory-only pass and
remain partial; the 737 undetermined rows require source assessment before any statement about reuse
or new mechanic families can be made.

## J. Recommended next execution phase

After explicit approval, begin with a small human-reviewed **PHB candidate validation cohort** from
the 48 inventory-only candidates. Verify the source text and candidate evidence, identify omitted
semantics, and compare production eligibility to the broader inventory predicate. Only then consider
generalizing that predicate. Follow with a PHB attack/scaling source cohort and a separate source-aware
comparison for XPHB and supplements. Measure false positives, full-source accounting and review
readiness before deciding whether new generic recognizers or composition rules are justified.

No extraction expansion or implementation began here. Step 7.4.4 remains COMPLETE, Step 7.4.3 remains
PARTIAL, and no later roadmap milestone was started.
