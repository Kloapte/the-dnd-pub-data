# Step 7.4.4C — Generalize Spell Condition Extraction

## Scope and observed gap

This batch extends the existing PHB condition patterns and typed context bindings. It does not add a
mechanic family, change the canonical model, run corpus-wide production extraction, or alter source
data, benchmark fixtures, review decisions, licensing metadata, or REST contracts.

Inspection of the pinned PHB catalog found two recurring gaps:

- Condition-inflicting structured fields often had a single authored saving throw and an explicit
  failed-save condition clause, but only five named owners received a typed save dependency. The
  corpus yielded 26 further single-ability dependencies when those clauses were checked directly.
- Thirty-two PHB Spells used condition markup without `conditionInflict` or `conditionImmune`
  classifications. The tags included removals, restrictions, immunities, negations, and prerequisites.
  Only explicit removal relationships were safe to type in this batch.

The reusable save matcher requires one structured save ability plus explicit source text linking a
failed save to an inflicted condition. One `SAVING_THROW_REQUIREMENT` claim is reused for all
conditions linked to that same failed save. Multi-ability cases such as Earthquake abstain when the
save-to-condition relationship cannot be disambiguated. Generic target phrases now provide a typed
target scope where the prose states one; duration and concentration continue to use the existing
source field bindings. Repeat-save success endings use the existing ending dependency and timing
binding only when the established explicit wording is present.

The reusable condition removal matcher covers an explicit ending clause, a condition list introduced
by “end one condition,” and a named effect that imposes a condition. It emits the existing
`ConditionChangeMechanic(REMOVE, ...)` payload with source text evidence, an explicit target when
available, pending review status, and the source revision. It does not interpret negations,
protection clauses, prerequisites, or a condition merely mentioned as an example as an `APPLY`
claim.

## Bounded production adoption

The selected newly convertible PHB owners are:

- Greater Restoration: remove charmed and petrified; exhaustion remains unsupported because the
  current `ConditionName` type has no exhaustion value.
- Lesser Restoration: remove one of four explicitly listed conditions.
- Power Word Heal: remove charmed, frightened, paralyzed, or stunned. The prone/stand-up clause is
  left unresolved because the source does not explicitly state that the condition ends.

The existing condition owner set gained 26 typed save requirements, bringing the production catalog
from 103 owners / 190 claims to 106 owners / 228 claims. The three new owners contribute ten
condition removal claims and two exclusive removal choice groups. All new claims remain partial, pending mechanics review, and
`NEEDS_REVIEW` for licensing. Existing claim IDs are retained; no previously processed owner lost a
candidate claim.

The follow-up semantic correction keeps Lesser Restoration's four existing individual `REMOVE`
claim IDs and links them to one `ConditionChoiceMechanic(REMOVE, ..., choicesToSelect=1)` group. The
source's disease alternative remains an explicit unmodeled diagnostic. Greater Restoration's
charmed/petrified removal claims now share a second one-of choice group; its exhaustion, curse,
ability-score, and hit-point-maximum remedies remain unmodeled. Power Word Heal's four condition
removals remain independent because its source does not limit them to one selection. The two groups
add two claims without changing any existing claim ID, evidence owner, source revision, review status,
licensing default, or private REST shape.

Mixed-effect review included Blinding Smite. Its source ties the Constitution save to the blinded
condition after the hit; the condition save is not reused as a dependency for its on-hit damage.
Damage extraction for that owner remains outside this condition batch.

preserved 7.4.4B inventory:

- Existing convertible owners gaining candidate claims: **26**.
- Additional potential typed claims: **38** (10 condition removals, 2 exclusive removal choice groups,
  and 26 saving throw requirements).
- The removal-choice correction adds two claims to the initial 7.4.4C result, with no newly convertible
  owners and no classification changes.
- Current classifications: **0 SUPPORTED, 163 PARTIALLY_SUPPORTED, 440 UNSUPPORTED, 366 NOT_ASSESSED**.
- The `CONDITION:SOURCE_CLASSIFICATION_WITHOUT_MATCHING_PATTERN` reason remains at **131**; this

  ambiguity/unsupported diagnostics, which raised total condition-related reason records from 133 to
  151. The two choice diagnostics preserve the restoration spells' other unmodeled alternatives.
- No inventory extraction failures occurred. Remaining source prose is still unassessed at
  `/entries` (952 records) and `/entriesHigherLevel` (967 records); because canonical assembly marks
  this coverage partial, no Spell is classified `SUPPORTED`.

The refreshed inventory is written to the existing 7.4.4A current-report paths. The original 7.4.4A
baseline and 7.4.4B comparison remain preserved. A separate 7.4.4B inventory snapshot provides the
before-state for the new [condition comparison](7.4.4C-condition-extraction-comparison.md).

## Validation

Focused tests cover failed-save condition application, a condition without a save, repeat-save
endings, simultaneous versus exclusive conditions, removal versus immunity/application, target
restrictions, negated and conditional condition references, multi-ability abstention, mixed damage
and condition triggers, duplicate save prevention, stable claim IDs, evidence associations, source
revisions, and review/licensing defaults. Regression coverage includes Shield, Fireball, Hold Person,
Blindness/Deafness, Bless, Mage Armor, Protection from Energy, all 7.4.4B production owners, and the
private inspection route.

Verification passed: focused extractor, inventory, and private REST tests (62 tests); the full Maven
suite (790 tests, no failures or errors); repeated inventory serialization and Markdown comparisons
(byte-identical); and `git diff --check`. Step 7.4.3 remains PARTIAL. Parent Step 7.4.4 remains IN
PROGRESS after 7.4.4C.
