## Existing model fit and gaps

The current `AttackRollMechanic` has `attackKind`, `actorRole`, `attackCount`, `attacksIndependent`
and `activationTiming`. It can describe a fixed number of independent attack rolls (including the
single attack used by existing attack spells). It cannot express an instance-count progression, a
target choice for each attack instance, whether an instance can re-use a prior target, or a
per-instance outcome-to-damage relationship. The `HIT`, `MISS` and `CRITICAL_HIT` values exist, but
`AppliesOnAttackRollOutcome` refers to a claim as a whole; it does not mean one corresponding damage
event for every individual roll.

`DamageMechanic` plus `CharacterLevelDamageScaling` models one damage amount and level tiers that
change that amount. It cannot state that each successful beam/ray independently produces that amount.
`SpellSlotScalingMechanic` supports damage and healing changes, not projectile/attack count changes;
using it for count would misstate the effect. A single `DamageMechanic` also cannot represent
Magic Missile's multiple independently assigned damage instances without implying one aggregate
damage event.

`SpellTargetSubject` and `TargetScope` represent single targets, multiple creature targets and
areas. They do not associate a particular target selection with each projectile/attack, express
repeat-target permission versus distinct allocation, or encode Magic Missile's visibility
requirement. A multi-target scope alone is insufficient. Claim references already bind a dependent
claim to a precise claim revision and content hash; retain those integrity guarantees and make
dependencies one-way from effect to triggering attack claim.

Four distinct shapes must remain distinct:

| Shape | Meaning | Candidate here |
| --- | --- | --- |
| A. Multiple independent attack rolls | Each instance has its own roll and HIT/MISS; per-hit effects correspond to that instance. | Scorching Ray; Eldritch Blast. |
| B. Multiple independently assigned damage instances without attack rolls | Each instance is assigned to a target and has automatic-hit semantics, with no attack claim. | Magic Missile. |
| C. One damage instance applied to multiple targets | One effect event affects a target set; not N independently allocated projectiles. | None of these three. Typical area effects may have this shape. |
| D. One attack roll affecting multiple targets | One roll governs multiple targets; not several independent rolls. | None of these three. |

Therefore `attackCount` plus `attacksIndependent` is necessary but not sufficient for A. It is not
the representation for B, C or D.

## Recommended minimal typed design (proposed, not implemented)

Keep existing payloads unchanged for single-instance spells. Add optional, omitted-when-absent
fields so their serialization and canonical hashes remain byte-identical. Do not revise any existing
claim merely to adopt the new shape. The following Java records/enums are a bounded design proposal,
not production code:

1. `InstanceCountProgression` (sealed interface), with `FixedInstanceCount(int count)`,
   `CharacterLevelInstanceCount(List<CharacterLevelInstanceCountTier> tiers)`, and
   `SpellSlotInstanceCount(int baseSlotLevel, int firstScalingSlotLevel, int instancesAddedPerSlotLevel)`.
   Tier counts mean total active instances at/after the threshold, not increments. Validate positive
   counts/levels, strictly increasing thresholds, no duplicate tiers, and a first threshold after
   the base level. For the two formula variants, validate the slope is positive and the first scaling
   level is greater than the base slot level.
2. `InstanceTargetAllocation`, containing a typed eligible `SpellTargetSubject`,
   `TargetSelectionCardinality` fixed to exactly one target per instance, and
   `TargetReusePolicy` (`REUSE_ALLOWED` or `DISTINCT_TARGETS_ONLY`). Keep the selected targets within
   the source-supported spell target set; for these cases repeat assignment is allowed. Optional
   typed targeting requirements can include `VISIBLE_TO_ACTOR` and `WITHIN_SPELL_RANGE`, rather than
   an untyped predicate. Scorching Ray's target category remains unknown until source eligibility is
   resolved; do not silently set it to creature. Eldritch Blast and Magic Missile use creature
   subjects.
3. Extend `AttackRollMechanic` with optional `InstanceCountProgression countProgression` and
   `InstanceTargetAllocation targetAllocation`. Existing `attackCount` is the base instance count;
   for Eldritch Blast it remains 1 and the character-level progression reports total counts 2/3/4 at
   levels 5/11/17. For Scorching Ray it remains 3 with slot progression adding one ray per slot
   above 2. Require `attacksIndependent=true` for a count above one. Target allocation attaches to
   each attack instance, not to the claim as a shared target set.
4. Add `AppliesOnEachAttackRollOutcome`, with a revision-bound attack claim reference, an explicit
   outcome (`HIT` for these spells), and an instance scope fixed to `CORRESPONDING_ATTACK_INSTANCE`.
   Attach it to the per-instance damage claim. It means each damage event is triggered by the
   corresponding individual attack's HIT; it does not aggregate damage or add one event per target.
   Validate the referenced claim is the same owner, is an attack-roll payload, and matches the exact
   claim revision and content hash. There is no reverse edge from the attack claim.
5. Keep `DamageMechanic` as the per-instance amount for A, with the new binding explicitly declaring
   its per-hit-instance meaning. For B, add a distinct `DamageInstanceSeriesMechanic` payload with
   `amountPerInstance`, damage type, `InstanceCountProgression`, `InstanceTargetAllocation`,
   `DamageResolutionMode.AUTOMATIC_HIT`, `EffectTiming.SIMULTANEOUS`, and
   `DamageRollGrouping` (`SHARED_ROLL`, `ROLL_PER_INSTANCE`, `UNSPECIFIED`). Magic Missile uses
   `UNSPECIFIED`, with a diagnostic retaining the source ambiguity. Automatic-hit means no attack
   roll is required for each valid selected target; it does not assert immunity to prevention,
   invalid targeting, or all other rules.

Do not add C or D via this change. If future sources require a single event across targets, model it
explicitly rather than overloading an instance series.

## Feasibility, eligibility and migration

Scorching Ray and Eldritch Blast share the same high-level implementation pattern: one independent
ranged spell attack per ray/beam, each instance is assigned one target, and each HIT has its own
damage instance. They can share the count/progression, allocation, and corresponding-hit binding
types. They differ in progression kind (spell slot versus character level) and in target evidence:
Eldritch Blast expressly names a creature; Scorching Ray does not name a category. Count and damage
must stay separate: Scorching Ray's slot scaling changes ray count, not 2d6; Eldritch Blast's level
progression changes beam count, not 1d10 per beam.

Magic Missile requires a distinct no-attack pattern. It has no attack outcomes to bind and instead
needs an automatic-hit damage instance series, target assignment, simultaneous timing, and slot-count
progression. It shares typed count and allocation concepts, but should not be forced into
`AttackRollMechanic` or `AppliesOnAttackRollOutcome`. Its damage-roll grouping remains unknown.

An implementation should be staged to reduce migration risk:

1. Add optional attack count progression/allocation and a corresponding per-attack outcome binding;
   test model validation and unchanged serialization for the existing 119 owners before activation.
2. Pilot Eldritch Blast only. Its explicit creature target, separate rolls, same/different target
   allocation, character-level thresholds and per-hit 1d10 make it the clearest attack-based case.
   Keep all review/licensing states pending and publication authorization at zero.
3. Add Scorching Ray only after a deliberate policy decision about its source-unspecified target
   category. Its count and per-hit damage are otherwise explicit. Preserve unknown/unsupported
   semantics if that question remains unresolved.
4. Add `DamageInstanceSeriesMechanic` separately and pilot Magic Missile. Preserve automatic-hit
   target conditions, simultaneous impact and slot scaling; leave damage-roll grouping unspecified.
   Retain the current benchmark fixture and its human-review authority exactly as it stands.

A common count/allocation vocabulary is worthwhile because the three spells share explicit per-
instance counts and one target assignment per ray/beam/dart. A common execution abstraction is not:
attack outcomes and automatic hit are different resolution semantics. Adding optional fields rather
than retrofitting all existing single-attack payloads avoids unnecessary claim revisions and keeps
their canonical serialization stable. In future, changing an attack claim's count or allocation
requires a revision and recalculated hash; a dependent per-instance damage binding must reference
the exact new revision/hash. An independent Magic Missile damage-series claim has no attack
reference.

Unsupported diagnostics should identify the exact missing semantic and source evidence: unresolved
target category for Scorching Ray, unspecified damage-roll grouping for Magic Missile, and any
future source ambiguity. Do not diagnose authored count/damage as unknown when the prose is explicit.
Do not mark the diagnostic resolved merely because an implementation can store an untyped string.

The existing Magic Missile benchmark fixture remains
