# Generic Mechanics Recognition Pipeline v2

## Architecture

The experimental startup path now consists of five explicit stages:

1. `MechanicSourceNormalizer` reads each pinned spell resource once and normalizes structured mechanic/context fields plus nested `entries` and `entriesHigherLevel` text into source-qualified fragments. Each fragment retains its owner, JSON pointer, entry hierarchy, source category and source-derived mechanic signals. PHB and XPHB remain distinct through their source-qualified owner and resource revision.
2. `MechanicTypeDeterminer` produces zero or more `MechanicCandidate` values for each fragment. Structured tags and authored prose can produce multiple candidate types; classification is not extraction.
3. `MechanicExtractionStrategy` implementations are registered by `MechanicStrategyRegistry`. The registry supports multiple deterministically ordered strategies per mechanic family, identified by strategy ID and version. The initial family strategies cover attack, damage, saving throw, condition, healing and scaling. They have no owner-ID or source-code allowlists. They emit only existing typed payloads when a bounded source shape is clear; unsupported relationships remain diagnostics. If strategies produce different payloads for the same family and fragment, composition retains the conflicting candidates and marks the owner `CANDIDATE_CONFLICT` rather than choosing one.
4. The composition stage assigns stable owner-scoped IDs, merges equivalent payload candidates, deduplicates evidence by resource and pointer, links mechanics that co-occur in one exact source fragment, validates mechanic/evidence references, and emits explicit duplicate, unresolved, ambiguous, conflict and unaccounted-fragment diagnostics. A co-occurrence link is not a dependency claim.
5. `SpellMechanicsInspectionCatalog` runs and caches this experimental result with the canonical catalog at startup. Requests only project the cached value.

This does not call the legacy adapter registry from the v2 recognition/extraction path. The legacy v1 experimental output remains available for the existing include contract and comparison. Canonical adapter eligibility, canonical documents, claim revisions, review, licensing and publication decisions are unchanged.

## Versioned API representation

The existing `?include=interpretedMechanics` response adds `experimentalInterpretationV2` alongside the unchanged canonical inspection and legacy `experimentalInterpretation` v1. It is omitted with the entire inspection include when the include is absent. In v2, `mechanics` contain typed properties and typed relationships only; `evidence`, `diagnostics` and `metadata` are separate collections/objects.

For a previously unprocessed owner such as `spell:phb:poison-spray`, the same include returns the canonical `NOT_ATTEMPTED` envelope and a separate v2 candidate. It does not put the candidate into canonical `interpretations`. A source fragment that yields signals but no safe payload appears in `diagnostics` (for example `INSUFFICIENT_SEMANTIC_RELATIONSHIP`); it does not become a mechanic with invented values. For `NO_PATTERN_MATCH`, `mechanics` may be omitted as empty and an explicit diagnostic states that no current strategy matched.

## Catalogue v2 results

See the deterministic machine-readable [per-owner results](generic-first-dry-run-v2-results.json) and [summary](7.4.4-generic-first-full-catalogue-dry-run-v2.md). The generator is [generate-generic-first-dry-run-v2.mjs](generate-generic-first-dry-run-v2.mjs). It requests the existing include and verifies each of the 969 source-qualified owners exactly once across 18 pinned resources.

| Measure | v2 result |
|---|---:|
| Owners evaluated | 969 |
| Owners with one or more typed candidate mechanics | 548 |
| Owners without a typed candidate mechanic | 421 |
| `CANDIDATE_PARTIAL` outcomes | 749 |
| `NO_PATTERN_MATCH` outcomes | 220 |
| Typed candidate mechanics | 1,026 |
| `EXTRACTION_ERROR` outcomes | 0 |
| `CANDIDATE_CONFLICT` outcomes | 0 |

Family counts: 4 `ATTACK`, 333 `DAMAGE`, 434 `SAVING_THROW`, 232 `CONDITION`, and 23 `HEALING`. Scaling currently classifies as an unsupported candidate and is not emitted as a mechanic because affected-mechanic relationships are not established by this first strategy set.

The v2 dry run recorded 356 damage-type ambiguities, 356 unresolved damage-application outcomes, 2,691 insufficient semantic relationships, 647 potential relationships left unextracted, 85 merged duplicates and 9,761 unaccounted source fragments. Diagnostic counts are occurrences, not unique owners or unique paths. The high count of partial outcomes is deliberate: fragment recognition is not spell completeness.

The v1 comparison used the preserved `generic-first-dry-run-results.json`: v1 has 351 candidate claims across 174 owners; v2 has 1,026 partial typed candidates across 548 owners. These are not directly equivalent claim populations. For the 129 canonical owners / 279 claims, v2's payload-only comparison reports 22 exact payload matches, 257 canonical payloads not reproduced, 1,004 additional experimental payloads and 152 additional payloads in a family also present canonically. The “changed same family” count is a subset of additional payloads. These numbers are diagnostic comparisons only and do not propose reconciliation.

## Verification and limitations

- All 175 pinned source JSON fingerprints verified with `analysis/mechanics/batch-11b-item-charge-syntax/verify-source-hashes.mjs`.
- The 969-owner v2 machine-readable and Markdown artifacts were generated twice after the multi-strategy update. Both files were byte-identical across runs: JSON SHA-256 `d628985683b498996aa01cd2d8556f0b3caa26fc2e4b1ba46d9d1de5752690aa`; Markdown SHA-256 `c169935ff4efc9160eaf94149f05afdbda567e990fa059d31bd8c2699bd89456`.
- The application started from compiled classes and the existing REST API returned canonical plus v1/v2 projections. An ordinary spell request omitted `interpretedMechanics`.
- Standard Maven test compilation remained affected by the Windows JDK archive-close `AccessDeniedException` against Jackson jars in the local Maven cache. To ensure the new assertions were actually run, I jarred the compiled main classes under `target/`, compiled both affected test sources directly with the cached test classpath, and invoked Surefire directly. The focused test compilation command was `javac -proc:none -cp target/classes-for-test.jar;<target/step-7.4.4X-test-classpath.txt contents> -d target/test-classes <test source path>` for each changed test file. Direct test compilation emitted the same archive-close exception on exit, but both new test class files were produced; direct Surefire then passed **36 tests across 2 suites**, 0 failures/errors/skips (4 generic pipeline tests and 32 API tests). The exact focused Surefire command was `mvnw -s target/maven-settings-generic-v2.xml -q -Djunit.jupiter.tempdir.cleanup.mode.default=NEVER -Dtest=GenericMechanicsRecognitionPipelineTests,SpellMechanicsInspectionApiTests surefire:test`. This establishes the new focused assertions were compiled and executed despite the standard lifecycle failure.
- The full precompiled suite passed through direct Surefire after the multi-strategy update: **894 tests across 104 suites**, 0 failures, 0 errors, 6 skipped. The focused suites include **37 tests** (5 generic pipeline tests and 32 API tests); the added PHB/XPHB isolation assertions were compiled and executed. The standard Maven lifecycle still does not complete because of the archive-close/compiler problem.
- The v2 projection is intentionally conservative and incomplete. It does not resolve save DCs, many damage types/outcomes, scaling targets, complex conditions, area relationships or mechanic dependencies across separate fragments. It does not claim full spell accounting. Runtime computation remains startup work; failure is surfaced per owner as `EXTRACTION_ERROR`.

The new JUnit source files are `src/test/java/com/thedndpub/data/mechanics/experimental/GenericMechanicsRecognitionPipelineTests.java` and additions to `src/test/java/com/thedndpub/data/spell/SpellMechanicsInspectionApiTests.java`. Their focused tests ran through direct Surefire. The full Maven lifecycle remains unverified because of the archive-close problem.
