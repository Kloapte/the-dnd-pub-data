# Step 7.4.4 Generic-First Spell Interpretation: Architecture and Pattern Audit

**Scope:** read-only audit of the existing source-aware Spell mechanics interpreter. No mechanics were
extracted for new owners, and no production code, tests, fixtures, pinned source data, inventory reports,
review state, licensing state, or publication decision was changed by this audit.

## 1. Executive summary

The mechanics document model is a useful foundation for scaling: it keeps typed claims, source evidence,
claim dependencies, source accounting, unsupported diagnostics, human review and licensing distinct.
The current interpreter is not yet generic-first in execution. It is a registry of eight ordered
top-level adapters, six of which are limited to one exact spell owner. The PHB adapter contains reusable
rule code, but also explicit owner lists, source-edition gates, exact phrase/formula checks and manually
composed branches. The runtime does automatically examine every catalogue owner against these registered
matchers; that does not mean it discovers arbitrary mechanics from source characteristics.

The reported **74 derivation-pattern IDs are provenance labels attached to claims**, not 74 executable
recognizers. Code inspection found eight registered adapter instances and four cross-owner rule
implementations worth treating as independently reusable capabilities at the implementation-unit level:
the Shield extractor, the PHB spell attack rules, the PHB save/damage generalizer and the PHB condition
rules. All four have bounded applicability or source constraints. Six registered adapters are
single-spell exceptions. The broader PHB adapter has substantial spell-specific dispatch and should not
be mistaken for a general PHB rules interpreter.

There is a real reuse path for already supported families: extend or broaden a matcher only after its
authored-text and structured-field predicates prove the same semantics and evidence can be retained.
The source-screening counts in the historical Q report provide leads, not current eligible-owner counts.
No honest current projection of additional supported owners can be made without source-by-source
assessment, which this audit intentionally did not perform.

**Conclusion:** the typed interpretation and provenance layers are ready to support a controlled
coverage-expansion phase, but current recognition and composition do not support broad, low-maintenance
automatic coverage by themselves. Start the next authorized phase with a read-only/applicability
separation and bounded generic-rule expansion; do not treat lexical candidates or the 74 labels as
coverage.

## 3. Existing architecture and execution flow

The startup path is:

1. `SpellMechanicsDocumentFactory` loads the pinned spell resources, builds source-aware owners and
   unattempted `MechanicsDocument` values, and records resource hashes and JSON pointers.
2. `SpellMechanicsInspectionCatalog` passes all definitions and unattempted documents to
   `SpellMechanicsExtractionService`.
3. The service calls `supports` on every registered pattern for each definition. The ordered registry
   requires zero or one match; two matches fail instead of applying precedence.
4. A selected matcher verifies the pinned source revision, extracts claims and diagnostics, and the
   source evidence verifier checks raw source bytes, owner pointer, source revision, evidence pointer,
   structured-value/text hashes and UTF-16 spans.
5. The resulting document is validated and projected to private inspection. No runtime dice, attack,
   target-selection, turn or effect execution occurs.

Thus the code does perform automatic discovery in the limited sense that every owner is offered to
every matcher at startup. New owners are interpreted automatically only when they satisfy an existing
matcher. Most matchers include exact owner IDs or fixed edition predicates, so similar source fields
or words do not make a new spell eligible.

`SpellMechanicsPattern` has only `patternId`, `supports` and `extract`. The registry has no rule
priority, confidence resolution, composition plan or overlap arbitration. One top-level matcher owns
each processed document. Multiple rule families can be emitted by the broad PHB extractor because it
manually dispatches and composes helper rules internally. `SpellCapabilityInventoryRunner` has a
separate inventory-only PHB support path (`supportsForInventory` / `extractForInventory`), so
candidate inventory eligibility and production runtime eligibility are not identical.

The model composes typed values and references declaratively: `MechanicPayload` is sealed; evidence
associations name claim paths; claim references bind owner-local ID/revision/content hash; dependency
validation rejects stale/missing relationships and cycles; document hash protocol 2 sorts claims by
stable identity; source verification is a separate operation from DTO construction. Coverage separates
`FULL_SPELL` and `DECLARED_SUBSET`, and complete source accounting can retain partial claims or
unsupported diagnostics. Review and licensing do not enter claim identity. These are reusable
architecture capabilities, not source recognizers.

## 7. Architecture scalability findings

| Concern | Observed behavior | Scalability consequence |
|---|---|---|
| Adapter selection | Each of eight adapters exposes `supports(SpellDefinition)`. Six require exact owner identity; others use bounded source characteristics or a fixed two-owner Shield edition list. | New owner coverage is possible only for predicates that were written to match it. The current distribution strongly favors owner-specific additions. |
| Generic discovery | The extraction service tests every definition against every adapter, then runs one unique match. | Automatic catalogue-wide offering exists, but there is no independent discoverable catalog of rules or generic feature recognizers. |
| Composition | Registry rejects overlapping adapter matches. `PhbSpellMechanicsExtractor` manually composes helpers; other top-level rules return their own document. | A single spell cannot generally receive several independent family rules from different adapters. Generic composition requires future explicit precedence/composition policy; none exists today. |
| Ambiguity and precedence | Overlap is a hard failure; no priority or best-match resolution exists. | Safer than silent precedence, but a new broad matcher can break startup if it overlaps a dedicated adapter. |
| Evidence | Source helpers attach authored text spans/structured-field references; source verifier checks trusted raw bytes and pointers after extraction. | Strong basis for reusable rules. A generic matcher must preserve exact originating path and source relation, not just parse normalized tags. Transformed evidence still depends on its input/transform records. |
| Dependencies | Exact revision/hash references and acyclic document graph validation are deterministic; rule execution order is fixed but claim identities do not depend on review/licensing. | Good for composing claims once a rule selects them. | Unsupported coverage | Unsupported constructs, unassessed paths, partial claims, `FULL_SPELL`/`DECLARED_SUBSET` extents and review readiness are explicit. | Good data model. | Review | Claims are `PENDING_REVIEW` or escalated; the three FULL_SPELL scopes are identifiable as human-review ready. | Data is reviewable, but no batch review queue/workflow is part of the interpreter. Six benchmark fixtures still await human adjudication. |
| Edition expansion | PHB/XPHB/XGE/AU/TCE revisions are distinct and source validators pin edition resource hashes. | Safe isolation exists. Broadening a PHB matcher to XPHB or another book must be an explicit, separately source-verified rule. |
| New source books | Source edition enum and adapter predicates are closed to current values. | Adding sources requires explicit fingerprint policy and interpretation evidence, but not necessarily one adapter per spell. |

### Completeness and review boundary

`PROCESSED` answers whether extraction was attempted. Owner coverage answers whether the declared
source scope was accounted for. Claim completeness answers whether a bounded mechanic claim preserves
its own assessed semantics. Human review answers whether a human approved/rejected a specific claim
revision. Licensing answers whether the content has an independent rights basis. Publication
authorization is a further separate decision. Existing tests and DTOs preserve these separations;
future dashboards should report each axis independently rather than one aggregate “supported” count.

The three current FULL_SPELL scopes establish that the model can represent source-accounted scopes
with an explicit unsupported range detail and partial attack claim. This is a targeted precedent, not
evidence that arbitrary spell JSON can be completely accounted automatically. `COMPLETE_WITHIN_SCOPE`
is only reliable when the adapter explicitly enumerates source identity, structured mechanics fields,
entries and higher-level entries (and any other relevant path) or records why a path is irrelevant.

## 8. Coverage expansion opportunities, ranked by reuse potential

1. **Reuse the PHB condition recognizer on source-characteristic matches already supported by its
   predicates.** Audit the current 840 untouched owners with a non-mutating candidate report first;
   do not assume every tagged condition is a grant/removal or that the recognized phrase is sufficient.
   A future batch can process only manually reviewed source candidates and compare full coverage paths.
2. **Generalize save-plus-damage grammar from the existing eight-owner allowlist.** First compare
   source-backed examples that exactly match the current recognizer's single save, single damage
   formula and failed-save grammar. Expand only the predicate after negative cases cover false-positive
   text, successful-save damage, multiple formulas and target scope. No current eligible-owner count
   is verified.
3. **Generalize the PHB single-attack/cantrip rule surface.** Separate reusable parts (attack kind,
   caster, cast-time, hit binding, cantrip tiers) from special-owner branches (Melf's Acid Arrow,
   attack modifiers, movement, recovery prevention). Candidate screen count of 75 attack-related
   owners is a historical lexical lead, not a projection.
4. **Reuse typed amount/scaling parsing for common structured progressions.** Preserve progression
   semantics (slot versus character level, per-instance versus damage) and require authored-text
   evidence for timing and applicability.
5. **Add a generic composition mechanism only when a demonstrated candidate needs it.** The current
   one-adapter rule and PHB manual composition should first be tested against source candidates. Avoid
   speculative plugin/priority frameworks; a deterministic plan can be smaller and explicit.
6. **Create new reusable recognizers for repeated mechanic gaps.** Q–X examples expose recurring
   classes—delayed outcomes, persistent activations, consumable spell objects, outcome-independent
   areas, conditional chains—but the samples are not enough to generalize each family broadly. Gather
   a small source-diverse cohort before adding a generic recognizer.
7. **Retain spell-specific adapters for exceptional source structures.** Keep owner-specific rules
   only when several source examples fail to fit a simple generic rule without losing a qualifier.
   Record why the limitation is structural or semantic and keep source evidence in the adapter.

## 9. Risks, limitations and unresolved questions

- **Owner allowlists dominate.** The broad PHB class is a manually curated dispatcher; beyond it,
  most adapters do not generalize. Reuse growth requires matcher engineering and candidate assessment.
- **No multi-adapter composition.** One owner can match at most one top-level adapter. The internal PHB
  case is special composition, not a general rule planner.
- **No rule precedence.** Overlapping support predicates fail. That invariant is safe, but generic
  matching will expose overlap decisions that need an explicit policy.
- **Inventory versus production eligibility differs.** The inventory's PHB candidate hook can inspect
  broader source cues than the startup production support predicate. Keep candidate discovery
  non-authoritative and do not infer runtime coverage from its classification.
- **Coverage relies on adapter path declarations.** Complete source accounting is representable, not
  automatically guaranteed by enumerating JSON fields.
- **The 74-ID statistic is easy to misread.** It measures derivation metadata, not 74 independently
  executable or reusable recognizers.
- **Sample size.** The eight registered adapter patterns are drawn from five source revisions and a
  few families. The current tests establish key local invariants but do not adjudicate all 279 claims
  against a human-reviewed gold corpus.
- **Review/licensing throughput.** All claims still need human review and licensing assessment; the
  model has status fields but no batch review workflow in this interpreter.
- **Source expansion.** Thirteen catalogue source codes have no current interpreted-claim revision;
  source-specific fingerprints and wording must be reviewed before reuse.
- **HTTP deployment boundary** is documented separately in the private inspection contract and is
  not changed or reassessed by this interpretation scalability audit.

Unresolved design questions for a future authorized phase: Should candidate matching and production
eligibility be separate interfaces? What minimal rule-composition representation is needed for
different families to contribute claims to one owner? Should full-scope path accounting be generated
from a source manifest plus explicit relevance decisions? How will humans review large batches while
binding decisions to claim hashes and leaving licensing independent?

## 10. Recommended next execution phase

After explicit authorization, begin with a **bounded generic-rule applicability phase** rather than
new mechanic families:

1. Define a read-only candidate report that runs source predicates without producing canonical claims
   or changing the authoritative inventory. Include source edition, exact pointers, match predicates
   and rejection reasons.
2. Select a small set of additional owners whose authored text and structured fields match an existing
   PHB condition or failed-save/damage rule exactly. Human-review the source matches before enabling
   production extraction.
3. Separate reusable matcher logic from owner eligibility lists only where this cohort demonstrates
   identical semantics. Add negative tests from near-miss candidates and verify full source accounting.
4. Compare before/after canonical, private inspection and default REST outputs, source fingerprints,
   inventory classifications and hash/review/licensing invariants.
5. Measure the extra processed and source-accounted owners; do not project full-catalog coverage until
   observed precision and review throughput support it.
