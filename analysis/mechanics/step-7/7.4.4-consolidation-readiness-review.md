# Step 7.4.4 Consolidation and Readiness Review

**Decision: CONDITIONAL GO.** The typed mechanics layer is a sound bounded interpretation
architecture for the pilot families, but three material conditions remain before the parent step is
closed: document-order/hash behavior needs an explicit canonicalization decision, the three legacy
PHB cantrip owners with PARTIAL coverage need explanatory coverage state, and the canonical evidence
span validation trust boundary needs a documented decision with matching negative tests. The unprotected
private inspection route is a high-severity release-boundary risk and must be gated before any
internet-facing deployment. This review does not authorize remediation or public deployment.

Step 7.4.4 remains **IN PROGRESS**. Step 7.4.3 remains **PARTIAL**. All A–X pilot statuses are left
as recorded.

## 1. Executive summary

The architecture has useful, independently inspected boundaries for immutable typed mechanics,
source revisions, evidence, assessment, human review, licensing, and publication decisions. Claim
references carry owner-scoped IDs, revisions, and hashes; the validator detects unresolved or stale
references and escalates effective review. Representative attack, damage, save, activation, area,
object-use, and chain relationships are represented without a combat executor. Current claims remain
unverified and unlicensed.

The current inventory contains **969 source-aware Spell owners**, **129 processed owners**, and
**279 interpretations**. Of the 129 processed owners, 126 have PARTIAL coverage and three have
NONE_SUPPORTED coverage; no owner has COMPLETE_WITHIN_SCOPE coverage. Claim completeness is a
separate measure: 62 claims are COMPLETE_WITHIN_CLAIM and 217 are PARTIAL. Review state is also
separate: 80 claims are PENDING_REVIEW and 199 NEEDS_MECHANICS_REVIEW. All 279 licensing assessments
are NEEDS_REVIEW. No claim is VERIFIED, and publication authorization is zero.

I verified two medium-severity architectural gaps directly: the document hash preserves list order,
so reordering otherwise identical claims changes the document content hash; and the conditional
attack-chain validator embeds Chromatic Orb-specific assumptions in generic model validation. I also
reconfirmed the older coverage-quality concern for Chill Touch, Ray of Frost, and Shocking Grasp:
their owner coverage is PARTIAL, their claims are all COMPLETE_WITHIN_CLAIM, but the current coverage
projection has no unassessed paths and no unsupported diagnostic explaining the remaining partial
owner status.

The largest security concern is that the opt-in `interpretedMechanics` representation is labeled
`PRIVATE_INSPECTION`, but is served through a `permitAll` `/api/**` rule and is not filtered through
publication approval. This is consistent with the roadmap's current private-network deployment
assumption, but it is not an enforced private/public boundary. Treat the high-severity finding as a
release blocker before internet exposure; it is not evidence that the application is currently
internet deployed.

The test suite is green and the 175 pinned resource hashes verify. Those tests establish structural
and deterministic behavior; they do not independently adjudicate correctness against human-reviewed
gold fixtures. All six spell benchmark fixtures remain PENDING_HUMAN_REVIEW.

## 4. Mechanic-family assessment

The canonical model uses immutable Java records, a sealed `MechanicPayload`, enums/value objects,
and defensive copies. The following classification is based on actual responsibility and validator
behavior, not type count. “Reusable with limitations” means another spell can use the structure, but
must preserve its explicit scope and diagnostics; it does not assert universal game-system coverage.

| Payload kind | Classification | Responsibility / qualification |
|---|---|---|
| ATTACK_ROLL | REUSABLE_WITH_LIMITATIONS | Attack type, actor, count, timing, target allocation, and progressions; not an attack resolver. |
| DAMAGE | REUSABLE | One typed amount/type with outcome or activation relationships in context. |
| SAVING_THROW_REQUIREMENT | REUSABLE_WITH_LIMITATIONS | Ability/subject/DC qualifiers and explicit result bindings; no runtime save/DC evaluator. |
| DAMAGE_INSTANCE_SERIES | REUSABLE_WITH_LIMITATIONS | Finite source-supported automatic-hit instances and allocation; deliberately not a general scheduler. |
| SPELL_SLOT_SCALING | REUSABLE_WITH_LIMITATIONS | Typed dice/count scaling; each subtype must preserve threshold and base semantics. |
| EFFECT_DURATION | REUSABLE | Duration claim/reference; not a lifecycle engine. |
| PERSISTENT_SPELL_EFFECT | REUSABLE_WITH_LIMITATIONS | Spell-created non-creature persistent effect, explicit establishment/activation/termination qualifiers; no state manager. |
| ENCHANTED_OBJECT_COLLECTION | REUSABLE_WITH_LIMITATIONS | Finite per-object enchantments and use consumption; no object identity, inventory, or mutation. |
| ATTACK_TRIGGERED_AREA_EFFECT | REUSABLE_WITH_LIMITATIONS | Static attack-relative area and outcome-independent trigger; no spatial query. |
| CONDITIONAL_ATTACK_CHAIN | REUSABLE_WITH_LIMITATIONS | Static conditional follow-on opportunities; current validator hard-codes XPHB Chromatic Orb assumptions (F-03). |
| ATTACK_ROLL_MODIFIER | REUSABLE_WITH_LIMITATIONS | Conditional advantage/disadvantage and attack selectors; does not calculate rolls. |
| CONDITION_CHANGE | REUSABLE | Typed application/removal and condition timing/subject. |
| CONDITION_CHOICE | REUSABLE_WITH_LIMITATIONS | Bounded choice over explicit referenced condition claims. |
| DAMAGE_RESISTANCE | REUSABLE | Explicit damage type/operation scope. |
| SPELL_DAMAGE_PREVENTION | REUSABLE_WITH_LIMITATIONS | Bounded source-supported prevention; not general mitigation math. |
| HEALING | REUSABLE | Typed amount and mode, with symbolic operands. |
| ARMOR_CLASS_MODIFIER | REUSABLE | Typed AC operation/amount. |
| STATISTIC_MODIFIER | REUSABLE_WITH_LIMITATIONS | Typed statistic operation; not a general character-stat engine. |

The adjacent `MechanicFamily` enum has 19 broader values; several payload kinds intentionally map
to a coarse family (for example duration/effect duration and prevention subtypes). This is not a
one-to-one enum defect because payload kind carries the precise type. Amount expressions (`DICE`,
`SUM`, symbolic ability modifiers) and explicit source/target roles avoid arithmetic or actor
conflation. No evaluated character statistics or mutable combat states are produced.

The main extensibility caveat is not that a type is spell-specific in name; it is that the generic
conditional-chain validator currently encodes d8, one initial cast-time ranged attack, a particular
target-reuse policy and slot/leap progression. That is a real constraint on reuse, detailed in F-03.

## 5. Cross-claim integrity

**Verified in code and focused tests:** claim IDs are constructed as `mechanic:<owner-id>:<slot>`;
the record pins revision number and SHA-256 over `MechanicRevisionContent`. The content includes
payload, context, evidence associations, derivation and assessment, but excludes human review and
licensing state. Therefore review/licensing changes do not silently change mechanic identity.
`MechanicsBindings` exposes typed dependencies; `MechanicsDocumentValidator` requires current
owner-local references and compares exact ID/revision/hash. Missing and stale references produce
required-review findings; dependencies on rejected or review-needed claims propagate
NEEDS_MECHANICS_REVIEW. This preserves uncertainty instead of promoting a broken relationship.

The graph is declarative. The current Chromatic Orb graph is acyclic: attack claim → damage claim →
conditional-chain claim (the chain also references the attack); there is no recursive claim edge for
later leaps. The runtime event sequence is described as data and does not create runtime attack
objects. Ice Knife has attack → explosion → save → cold damage, plus attack → HIT piercing damage.
Witch Bolt has attack → HIT-gated link → later action damage, plus attack → initial damage. The other
pilots similarly use explicit revision-bound attack/save outcomes. Dependencies are independent of
claim ordering in the extractor and references never encode a future dynamic event as a new static
claim.

**Ordering caveat:** `MechanicsHashes.documentHash` hashes the `MechanicsDocumentContent` record with
Jackson property ordering, but its `interpretations` list is copied without sorting. Reordering the
same set of claims therefore changes document bytes and hash. Individual claim hashes remain
independent of sibling order. Extractors currently produce deterministic order, so repeated
projection is stable; the stronger invariant “claim ordering does not change canonical results” is
not satisfied. See F-02.

**Inspected but not fully proven as a model-wide invariant:** dependency resolution is current and
hash exact, but the validator does not have a general explicit dependency-DAG/cycle rejection pass.
Evidence relationships have a cycle check; mechanic references are processed in bounded validation
passes. The checked pilot graph is acyclic, and a self-referential Ice Knife construction is rejected
by specialized binding rules. A general cross-payload cycle negative test is absent. Wrong-owner,
missing-target, and stale-hash cases are partly tested through specialized references and review
escalation, but not every binding subtype has an isolated negative test. Add a graph-level test as
part of the F-02 integrity decision.

An inspection limitation remains: `MechanicInspectionDto` contains claim ID and revision number but
does not expose that claim's content hash. A dependency serialized inside another claim contains the
pinned hash, yet an inspection client cannot compare it with the target claim hash from the same
projection. This does not weaken server-side validation, but reduces independent inspection
traceability (F-05).

## 7. Provenance and evidence assessment

Each claim's derivation carries a pattern ID/version and pinned artifact revision. Evidence types
distinguish authored text spans, structured fields, transformed evidence, and unavailable-origin
cases. `SpellMechanicsEvidenceSource` verifies resource SHA-256 against the owner revision, resolves
source JSON pointers, validates structured values against the pinned raw JSON, and locates authored
phrases using Java `String` indices. Java indices are UTF-16 code units; spans are end-exclusive.
Stable evidence IDs include source fingerprint, owner/pointer and span. Tests cover UTF-16 offsets,
resource mismatches, evidence joins, deterministic IDs, and evidence claim paths.

The evidence graph and association hashes are structurally validated. `MechanicRecord` resolves
claim paths against canonical claim JSON; evidence IDs and hashes must resolve; source artifact
revisions must match the document. Pilot reports and tests verify focal authored spans and structured
fields. The 175-file source-hash verifier passed.

There is a distinction between **structural validity** and **semantic sufficiency**. A valid span,
pointer, and digest prove which bytes are cited, not that the cited phrase fully supports the
mechanical conclusion. This audit checked representative pilot citations and source-owner
separation, but did not independently re-adjudicate all 279 claims. In addition, extraction validates
span construction against loaded source strings; the canonical document model does not itself have
the full source text available to recheck a deserialized span's upper bound or surrogate boundary.
The syntax corpus and benchmark validators exercise bounds on their own paths, but a generic
canonical-document negative test for an out-of-range text span is missing. Record this as a medium
test/integrity gap, not as evidence that a currently generated claim has an invalid span.

XPHB Chromatic Orb evidence is bound only to XPHB `/spell/48`, file SHA
`442544a91aad1181cbad78d49cfa48f9ced7d8b048dbc781e32fa6fefc6278b9`; the PHB 2014 source is a
separate `/spell/46` and is not an input to that adapter. No source resource was edited.

## 8. Coverage and diagnostics

Coverage is a bounded assessment over declared source paths, not a claim that all prose in an owner
has been interpreted. `NOT_ATTEMPTED` differs from processed `NONE_SUPPORTED`; PARTIAL differs from
claim-level COMPLETE_WITHIN_CLAIM; COMPLETE_WITHIN_SCOPE is guarded by the validator and is not
currently emitted. `SOURCE_UNSPECIFIED` is used where authored wording leaves a fact open (for
example target category or Magic Stone sling range); `FAMILY_NOT_IMPLEMENTED` indicates a known
mechanic lacks a typed representation; ambiguity reasons retain unresolved source meaning.

The current family/reason counts are useful for audit but do not cover all owner PARTIAL states.
The capability inventory also uses its own aggregate classification algorithm. Do not read the
174 PARTIALLY_SUPPORTED inventory owners as the same population as 126 processed PARTIAL coverage
owners.

The general PHB `SpellMechanicsAssembly.finish` currently assigns PARTIAL whenever it has one or
more records (`src/main/java/com/thedndpub/data/mechanics/spell/SpellMechanicsAssembly.java:136-142`).
This is conservative, but it means that generic assembly cannot express a fully assessed owner
scope even where the extractor has assessed all considered source paths. Specialized pilots set
coverage explicitly and also currently remain partial. The validator does support
COMPLETE_WITHIN_SCOPE, but no current owner exercises that status.

The specific prior concern is still present. Current private inspection documents show:

| Owner | Owner coverage | Claims | Claim completeness | Unassessed paths | Unsupported diagnostics |
|---|---|---:|---|---:|---:|
| `spell:phb:chill-touch` | PARTIAL | 4 | all COMPLETE_WITHIN_CLAIM | 0 | 0 |
| `spell:phb:ray-of-frost` | PARTIAL | 3 | all COMPLETE_WITHIN_CLAIM | 0 | 0 |
| `spell:phb:shocking-grasp` | PARTIAL | 4 | all COMPLETE_WITHIN_CLAIM | 0 | 0 |

Their declared considered paths include `spellAttack`, `damageInflict`, `entries`, and
`scalingLevelDice`; however, no unassessed or unsupported reason is serialized to explain why the
owner remains PARTIAL. This matches Q's previously reported traceability gap. The bounded claims
may be semantically complete for their own contexts while owner coverage remains partial, but the
unexplained status prevents an inspector from seeing the boundary. No status should be upgraded by
guessing.

Chromatic Orb's four diagnostics (range, external/critical damage dice, later-attack miss, and target
category) represent distinct unresolved model/source questions. The authored XPHB record does not
settle later miss behavior or the scope of external/critical dice; attack range is a missing typed
field; and target category is not delimited enough for the model. The reports mark the chain PARTIAL.
These are not “known rules” that should be filled from PHB 2014 or generic conventions. Ice Knife
and Witch Bolt similarly retain explicit range/DC diagnostics where the model lacks a source-backed
qualifier. No reviewed pilot claim appears COMPLETE_WITHIN_CLAIM while omitting one of its own
declared essential qualifiers; completeness concerns are owner-scope explanation and generic
validator breadth, not a discovered incorrect value in these ten focal claims.

## 9. Review, licensing, and publication boundaries

The internal mechanics record keeps review and licensing outside claim content hashes. New
interpretations default to PENDING_REVIEW; dependency and required-review findings can make the
effective state NEEDS_MECHANICS_REVIEW. Licensing is represented independently, and all current
claims are NEEDS_REVIEW. No benchmark fixture is human-approved; candidate comparisons cannot
produce VERIFIED status. Publication authorization is zero.

Default Spell REST responses omit interpreted mechanics. An unauthenticated opt-in request for
`/api/spells/spell%3Axphb%3Achromatic-orb?include=interpretedMechanics` returned an available
`PRIVATE_INSPECTION` projection in a local application run. `SpellsService` attaches the full
inspection projection on that request, and `SecurityConfig` permits `/api/**` to all requests. The
mechanics route does not consult the publication catalog. Thus “private” is currently a contract
label plus deployment assumption, not an authorization boundary. The roadmap explicitly says the
owner runs on a private network and defers Keycloak/public internet deployment; this finding does not
claim an external attacker currently has network access. Before internet exposure, backend
authorization and publication gating must be implemented and tested. See F-01.

## 11. Findings register

### F-01 — Opt-in private inspection is not access-controlled

- **Severity:** HIGH.
- **Files/locations:** `src/main/java/com/thedndpub/data/util/SecurityConfig.java:23`;
  `src/main/java/com/thedndpub/data/services/SpellsService.java:69-100`;
  `src/main/java/com/thedndpub/data/controllers/SpellsController.java:30-47`;
  `src/main/java/com/thedndpub/data/mechanics/inspection/SpellMechanicsInspectionMapper.java:34-45`.
- **Observed:** all `/api/**` routes are permitted to all requests. A local unauthenticated request
  with `include=interpretedMechanics` returned the complete `PRIVATE_INSPECTION` including
  unreviewed evidence and NEEDS_REVIEW licensing metadata. The default response does omit it.
- **Expected invariant:** private mechanics must stay behind an enforced private boundary; eventual
  public responses must apply backend authorization/publication policy rather than rely on an
  `include` name or frontend filtering.
- **Evidence:** source inspection, local HTTP request, API projection tests, and roadmap statements
  that internet deployment/auth are deferred.
- **Impact:** if network exposure changes without a backend gate, unreviewed and unlicensed
  third-party mechanics/provenance are returned to any caller. `PRIVATE_INSPECTION` is descriptive,
  not access control.
- **Recommended remediation:** before internet-facing deployment, separate/private-gate this
  projection and test unauthenticated/unauthorized requests plus publication decisions. Do not treat
  this audit as permission to change policy.
- **Required before closing 7.4.4:** **No**, under the roadmap's current private-network-only
  deployment boundary; **yes before any internet-facing release**. Record the deployment constraint
  as an explicit accepted limitation if Step 7.4.4 closes first.

### F-02 — Document hash is sensitive to claim list ordering

- **Severity:** MEDIUM.
- **Files/locations:** `src/main/java/com/thedndpub/data/mechanics/model/MechanicsDocumentContent.java:10-25`;
  `src/main/java/com/thedndpub/data/mechanics/model/MechanicsHashes.java:12-18,55-61`;
  `src/test/java/com/thedndpub/data/mechanics/model/MechanicsDocumentTests.java`.
- **Observed:** canonical JSON sorts object properties and map keys, but document lists are copied in
  their supplied order and hash v1 serializes them without sorting. Reordering the same set of
  interpretation records changes `documentHash`; tests exercise stable round-trip/order-preserving
  serialization, not order-independent canonical results.
- **Expected invariant:** the requested audit invariant says claim ordering should not change
  canonical results, while preserving deterministic evidence ordering where order is meaningful.
- **Evidence:** implementation of the hash path and list defensive-copy constructor; current tests
  contain no order permutation equivalence assertion.
- **Impact:** equivalent claim sets assembled by different deterministic adapters can acquire
  different document fingerprints. Individual mechanic claim hashes are unaffected.
- **Recommended remediation:** decide whether interpretation order is semantic. If it is not, define
  canonical sorting for the document hash protocol and add permutation tests; if it is, document that
  order is identity-bearing and revise the stated invariant before future consumers rely on set
  semantics. Do not silently alter hash protocol v1.
- **Required before closing 7.4.4:** **Yes, decision and test required**; changing hash behavior itself
  requires an explicitly versioned protocol/migration decision.

### F-03 — Conditional-chain validation is Chromatic Orb-specific

- **Severity:** MEDIUM.
- **Files/locations:** `src/main/java/com/thedndpub/data/mechanics/model/ConditionalAttackChainMechanic.java`;
  `src/main/java/com/thedndpub/data/mechanics/model/MechanicsDocumentValidator.java:158-206`;
  `src/main/java/com/thedndpub/data/mechanics/spell/XphbChromaticOrbRules.java`.
- **Observed:** the generic payload validator requires one cast-time caster ranged attack, a single
  unspecified target category, d8 damage, matching at least two d8 faces in one spell damage roll,
  a particular creature reuse policy, previous-target distance, and a slot-level leap curve. Its
  error messages explicitly name Chromatic Orb.
- **Expected invariant:** mechanic payloads should enforce their own generic type invariants while
  owner-specific source constraints remain in adapter/claim validation.
- **Evidence:** specialized validator branch and the sole current conditional-chain owner/test.
- **Impact:** a later non-Chromatic conditional chain using another die, actor, trigger or target
  policy will be rejected despite fitting the declared payload kind. The mechanic kind is
  REUSABLE_WITH_LIMITATIONS, not demonstrated reusable across independent spells.
- **Recommended remediation:** decide whether this is an intentionally single-owner pilot type. If
  it is meant as shared architecture, move source-specific rules into a typed policy or adapter-level
  invariant and retain generic graph/reference validation in the model.
- **Required before closing 7.4.4:** **No**, if its one-owner bounded status is explicitly accepted;
  otherwise required before claiming conditional chaining as a reusable family.

### F-04 — Three partial PHB owners have no coverage explanation

- **Severity:** MEDIUM.
- **Files/locations:** `src/main/java/com/thedndpub/data/mechanics/spell/SpellMechanicsAssembly.java:136-142`;
  current private inspection for `spell:phb:chill-touch`,
  `spell:phb:ray-of-frost`, and `spell:phb:shocking-grasp`; `PhbSpellMechanicsExtractor` coverage
  assembly; `analysis/mechanics/step-7/7.4.4Q-multi-instance-consolidation-discovery.md` §7.
- **Observed:** each owner has PARTIAL coverage, zero unassessed paths, zero unsupported diagnostics,
  and all three/four emitted claims are COMPLETE_WITHIN_CLAIM. Considered source paths are recorded,
  but the inspection does not state why owner coverage remains partial.
- **Expected invariant:** PARTIAL owner status should expose the omitted/unassessed path or
  diagnostic that explains its boundary, even when every bounded claim is complete.
- **Evidence:** current 129-owner inspection snapshot and Q's earlier report. The current inspection
  reproduces the gap after Chill Touch and Shocking Grasp gained their modifier claims.
- **Impact:** an inspector cannot distinguish intentionally bounded coverage from stale or
  accidental partial status; aggregate coverage is less auditable.
- **Recommended remediation:** add explicit unassessed paths or a typed coverage rationale to each
  owner, grounded in a source review. Do not upgrade coverage merely because no diagnostic exists.
- **Required before closing 7.4.4:** **Yes**, or document and approve a consistent alternate
  meaning for PARTIAL with no reason path.

### F-05 — Private claim projection omits the target content hash

- **Severity:** LOW.
- **Files/locations:** `src/main/java/com/thedndpub/data/mechanics/inspection/MechanicInspectionDto.java:12-23`;
  `MechanicRevision.java`; `MechanicsRevisionReference`/`MechanicRevisionReference` types.
- **Observed:** internal claims carry content hashes and dependents expose exact reference hashes,
  but the projected target mechanic exposes only ID and revision number.
- **Expected invariant:** an inspection consumer should be able to verify claim-to-claim references
  from one private projection when the contract promises exact hash references.
- **Evidence:** DTO field list compared with `MechanicRevision` and cross-claim context serialization.
- **Impact:** server validation remains sound, but an external private-inspection auditor cannot
  independently compare a dependent's pinned SHA with the target's SHA without another data path.
- **Recommended remediation:** consider exposing the revision content SHA in the private
  inspection DTO (not public default output) and test reference resolution. Preserve the existing
  canonical claim hash protocol.
- **Required before closing 7.4.4:** **No**; useful for inspection interoperability.

### F-06 — Canonical evidence-span bounds are not revalidated from source bytes

- **Severity:** MEDIUM.
- **Files/locations:** `TextMechanicsEvidence.java`; `SyntaxSpan.java`;
  `MechanicsDocumentValidator.java:33-47`; `SpellMechanicsEvidenceSource.java`.
- **Observed:** production extraction constructs spans from loaded source text and hashes the text;
  generic document validation verifies artifact revision and evidence relationships but has no source
  bytes to prove the end bound or Unicode boundary of a deserialized span. The syntax corpus and
  benchmark paths have span checks, while the generic canonical-document test path lacks the
  requested malformed persisted-span negative case.
- **Expected invariant:** evidence accepted as canonical should either be validated against source
  text or explicitly carry a verification status proving it was created by the trusted source-aware
  builder.
- **Evidence:** evidence constructors and validator have no resource-text argument; extractor does
  validate spans during construction; no generated current span defect was found.
- **Impact:** direct or future persisted canonical input could carry a structurally valid digest and
  out-of-range span unless it passes the trusted extraction path. This is a validation gap, not a
  discovered production evidence error.
- **Recommended remediation:** add a source-backed canonical validation path or constrain document
  construction to validated evidence; add end-bound and surrogate-split tests.
- **Required before closing 7.4.4:** **Decision required**. If canonical documents can only be built
  from the trusted builder today, document that trust boundary; otherwise validate before closure.

## 13. Recommended remediation

Before closing the parent step:

1. Resolve F-02 by either making document hash canonicalization order-independent under a versioned
   protocol, or explicitly deciding that ordered claims are identity-bearing and updating the
   canonical-order invariant. Add a claim permutation test and a general dependency cycle test.
2. Resolve F-04 by explaining the remaining partial source scope for Chill Touch, Ray of Frost, and
   Shocking Grasp with source-reviewed path diagnostics/rationales; do not mark them complete by
   inference.
3. Decide and document the trusted evidence-construction boundary for F-06; add negative tests for
   invalid end offsets and UTF-16 surrogate splits if arbitrary canonical deserialization is in
   scope.
4. Record F-03 as an intentionally Chromatic-Orb-only pilot limitation or generalize its validator
   before describing conditional chains as reusable beyond this owner.
5. Keep F-01 on the release checklist. No change to authentication or publication policy is
   authorized by this audit; ensure private-network isolation remains an operational requirement
   until the approved backend gate exists.

Further pilots would add little confidence in the existing families. The A–X suite already includes
automatic hits, independent attacks, scaling, selected targets, HIT/MISS branching, persistent
effects, transferable consumed objects, outcome-independent areas, and conditional die-face chains.
The higher-value work is integrity/coverage tests and explicit readiness criteria, not another spell
that repeats a supported pattern.
